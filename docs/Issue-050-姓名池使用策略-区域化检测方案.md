## 一、问题反思：为什么「穷举姓名池 + 全局匹配」注定有天花板

Issue #45 之后暴露的误伤问题（详见 #49），根子不在某个正则写错了，而在**策略本身选错了方向**。

当前策略的隐含假设是：

> 「要脱敏的人 = 名单里已知的 7398 个人」+「凡是 姓+名字用字 组合的都是人名」

这带来三个结构性缺陷：

| 缺陷 | 表现 | 案例 |
|---|---|---|
| **召回天花板** | 名单外的人名（占实际人员的大多数）只能靠字符池"蹭"出来，漏脱风险高 | 「王根利」「李思远」「周慧敏」均不在 7398 名单内 |
| **误伤无上界** | 字符池笛卡尔积随扩池线性放大，业务词被无限误判 | 「天阳宏业」「渠道拓展」「工程项目组」 |
| **上下文被浪费** | 明明「成员：」这种上下文信号就在眼前，规则却只看字符 | 人工一眼能判断的事，机器判断不了 |

**关键洞察**：人做脱敏时，其实**从不逐个核对名单**。人的实际判断顺序是——

1. 先扫一眼版面，**哪些区域是「人名集中区」**？（表格的姓名列、正文里的名单段、落款签名区）
2. 再在**这些区域内**判断哪些条目是人名；
3. 区域之外，**默认不动**。

也就是说，人用的是**「区域优先」**的策略，而当前实现用的是**「全局逐字匹配」**的策略。这两者在召回和误伤上的表现差距极大。

## 二、思路：从「全局匹配」转向「区域优先的两阶段检测」

### 2.1 核心机制

```
阶段一：区域定位（Region Detection）
  ↓  在全文/全表上找出「姓名集中区」
  ↓  · 表格：列级判定（表头角色词 + 值列形态一致性）
  ↓  · 正文：列表结构判定（锚点词引导 + 候选同构性）
  ↓  姓名池在这里的作用 = 提供「形态原型」（姓 + 名用字），而非穷举名单
阶段二：区域内逐项判定（In-region Scoring）
  ↓  只在区域内做个体判断，不再全局撒网
  ↓  · D16 精确表命中 → 高置信，直接脱敏
  ↓  · 区域一致性（相邻项长度/形态一致）→ 中置信，脱敏
  ↓  · 区域外 → 不动（零误伤）
```

**这与人工的判断路径完全对齐**：区域化 = 人的「扫版面找名单区」，区域内核验 = 人的「在名单里逐个确认」。

### 2.2 姓名池在新策略中的角色转变

| 角色 | 旧策略 | 新策略 |
|---|---|---|
| **穷举名单**（7398 全名） | 唯一的召回来源 | 区域内的高置信锚点（种子） |
| **姓氏池 + 名字用字池** | 笛卡尔积全局匹配 → 误伤主因 | **形态原型**：判断「这串字长得像不像人名」 |
| **角色词/表头关键词** | 少数规则的触发条件 | **区域定位的主要依据** |

> 关键点：名字池从「匹配用的字符集」降级为「**形态判别的原型库**」。这样扩池的副作用大幅衰减——池里多几个常用字，只会让"长得像人名"的判断略松，不再直接制造误伤。

### 2.3 顺带发现：name_pool 混入了非汉字字符

实测 `scripts/config.json` 的 `name_pool`（1285 字）中含有 **17 个非汉字字符**：

```
Y L J S H C T N Z / 、 G E B X D K
```

其中：
- **15 个大写字母**（`X L J S H C T N Z G E B D K`）是脱敏占位符字符集的一部分（`replacement.NAME = "XXX"`、`ID_CARD = "XXXXXXXXXXXXXXXXXX"`、`DATE = "YYYY/MM/DD"` 等），**属必要实现，不能移除**——但它们会被规则A 当作"名字用字"，使「张三ABC」「李四X光」类混合串被误判为姓名。
- **2 个标点**（`、` `/）是**真正的污染**：扩充生僻字时误采，夹在生僻字中间（如 `…舜汛池统部…/…仝以、胡境…`）。它们直接导致「李思远、」被当作 4 字姓名，是名单整段吞并的直接原因。

> 因此 M9 的准确表述应为：**`name_pool` 移除标点类字符（顿号、斜杠），保留占位符字母**；字母类污染改由规则层的「姓名形态判定须全为汉字」约束来处理。

## 三、原型验证（已完成，实测数据）

### 3.1 通用业务语料（102 条非人名词组）

| 策略 | 误伤 | 误伤率 | 真名召回 |
|---|---|---|---|
| 当前实现（全局字符池粗筛） | 52 | **51.0%** | 12/12 |
| 仅区域化 | **0** | **0.0%** | 0/12 |

**区域化把误伤从 51.0% 直接降到 0.0%** —— 因为它**根本不在业务词上做判断**。

| 原文 | 当前实现 | 区域化方案 |

### 3.3 表格列级识别

| 表头 | 识别结果 |
|---|---|

## 四、方案设计：新增 N-C 层「姓名集中区检测」

### 4.1 架构位置与模块划分

```
当前：  全文 → 规则A（全局字符池粗筛）→ D16（精确表）→ 其他规则
新增：  全文 → 【N-C 区域定位】→ 区域化检测（高精度）→ 规则A（仅区域外，分级兜底）→ D16
```

N-C 层作为**前置的区域标注器**，输出「姓名集中区」的坐标集合，后续规则据此调整置信度。

**命名勘误**：原提案称新层为「N-B」，但 N-B 已被 Issue #16 占用（`common_rules.py:1852`「N-B 层：段落角色锚点扩散」，以及 `:1679` 的角色关键词三层扩展）。故新层改名 **N-C（区域检测层）**。

**模块划分建议（N-C 不并入 `table_role_detector.py`）**：

| 模块 | 职责 | 理由 |
|---|---|---|
| `scripts/table_role_detector.py`（现状） | **OOXML 格式适配层**：解析 PPT/XLSX（及新增 Word）XML，按坐标回写单元格 | 输入是 XML，处理的是格式结构 |
| `scripts/name_region_detector.py`（新增） | **语义判定层**：给一段文本判定「哪些区段是姓名集中区」，格式无关 | T2/T3 与表格无关，混入会让该文件变成大杂烩 |

N-C 对外接口为「区域判定 + 区域内分层打分」，各格式适配器（Word/Excel/PPT/PDF）调用之。**T1 表格列判定逻辑抽成共用函数**，由 `table_role_detector` 与 N-C 共同复用，避免两处实现漂移。

### 4.2 三类区域识别器

| 识别器 | 适用 | 判定依据 | 置信 |
|---|---|---|---|
| **T1 表格姓名列** | Word / Excel / PPT 表格 | 表头角色词 + 值列形态一致性 | 高 |
| **T2 正文名单段** | 段落/行内 | 锚点词引导 + 候选同构性 + 分隔符结构 | 高 |
| **T3 签名/落款区** | 文档末尾 | 位置特征 + 角色词 | 中 |

> **T2 定位说明**：T2 不是全新一层，而是**既有 N-B 层的升级版**。既有 N-B（`common_rules.py:1852` `_apply_anchor_expand_pass`）已能处理「核心组：蔡新发、张瑜、李明 → XXX、XXX、XXX」，但它是**固定句式触发**（角色词 + 冒号 + 整段扩散），不做同构性与形态校验，因此「需求包括、开发、测试、上线」这类也会被吃掉。T2 的实质是把 N-B 从**句式触发**升级为**区域判定 + 区域内同构打分**。

### 4.3 区域判定的三条准则

1. **结构性**：区域由分隔符（`、，,;；/`）连接的**同构项**构成（长度一致、形态一致）；
2. **上下文性**：区域前方 20 字内有角色/名单锚点词（成员、人员、名单、负责人、参会…），**或**区域内至少一项命中 D16 精确表；
3. **形态性**：每项满足「姓 + 1~3 个名用字」，或命中 D16 精确表。

> 三条准则**同时满足**才判定为姓名集中区 —— 这是把误伤压到 0 的关键。

### 4.4 区域内的个体判定（分层）

| 层级 | 条件 | 动作 |
|---|---|---|
| L1 精确 | 命中 D16 7398 全名 | 直接脱敏（高置信） |
| L2 同构 | 与区域内其他项形态一致（长度、姓氏/名用字构成） | 脱敏（中置信）—— **这是名单外人名能被捞出的关键** |
| L3 存疑 | 形态不完整 | 交 R4 评分层（#17）仲裁 |

### 4.5 与现有层的关系

| 层 | 定位 | 变化 |
|---|---|---|
| D16 精确表 | **全局常开，不进区域判定** | 不变，**仍是零漏脱的地基**；同时作为区域判定的**种子信号**（区域内至少一项命中 D16 即满足上下文准则） |
| 规则A 粗筛 | **降级为区域外唯一兜底** | 区域内不再走规则A（改用 L2 同构）；区域外仅在有弱上下文信号时启用，并按 #49 的 R2/R3 分级收紧 |
| N-A 表格角色列 | 扩展 | 从"表头关键词触发"升级为"表头 + 值列形态双重判定"（T1） |
| N-B 段落角色锚点扩散 | **升级为 T2** | 句式触发 → 区域判定 + 同构打分 |
| **N-C 区域检测层（新增）** | 区域标注器 | 格式无关，输出区域坐标集 |
| R4 评分层 | 升级 | 成为区域内的 L3 仲裁器 |

### 4.6 Word 表格接入（裁决点 3：必须补齐，且现状比原提案描述更严重）

**现状核对**：

| 维度 | PPT / Excel | Word |
|---|---|---|
| 走 `table_role_detector` | ✅ `redact_ppt.py` / `redact_excel.py` | ❌ **未接入** |
| 表头角色词表 | `_ROLE_COLUMN_HEADER_WORDS`（20+ 词，含「姓名/成员/组员/联系人/主讲/记录人」等） | `_TABLE_HEADER_COL_KEYWORDS`（`redact_word.py:1069`，**仅 12 词**：变更人/修改人/审核人/复核人/修订人/编写人/编制人/审批人/批准人/登记人/操作人/经办人/责任人/负责人） |
| 判定方式 | 表头角色词 → 列内批量脱敏 | 表头词仅作**触发条件**，列内仍走全局规则A |

**关键问题**：Word 表头词表**不含「姓名」「成员」「组员」「联系人」「参会人」**。因此 Word 表格里的「姓名」列**根本不触发列级脱敏**，只能靠规则A 在正文里逐字乱抓——而「姓名」列表头本身就在 102 条误伤语料内（「人员名单」同样在列）。这使 Word 成为规则A 误伤的主要放大器。

**补齐要点（Word 特有坑）**：

1. **合并单元格**：`w:gridSpan`（横向合并）/ `w:vMerge`（纵向合并）会导致列索引错位，必须按网格坐标还原真实列位，否则列级判定会串列；
2. **表头可能跨多行**：现实现只取前 2 行作为候选表头，区域化判定应按「表头行集合」聚合后再判列角色；
3. **文本被 run 拆分**：单元格文本常分布在多个 `w:t` 节点中，取文本与回写都要跨 run 处理（这是 Word 与 PPT/XLSX 最本质的差异）；
4. **词表统一**：Word 表头词表应与 PPT/Excel 共用同一份锚点词表（见 §4.7），不再各维护一份。

### 4.7 锚点词表：概念已有，问题是分散三处（裁决点 4）

**锚点词** = 「这一段大概率是名单」的触发信号词。这不是新概念，代码里已存在，但**分散在三处、口径不一致**：

| 位置 | 词表 | 用途 |
|---|---|---|
| `common_rules.py:1683-1700` | `_ROLE_KEYWORDS_CORE` / `_ROLE_KEYWORDS_GENERAL` / `_ROLE_KEYWORDS_GROUP`（分核心/通用/分组三层） | 段落角色词，喂 `_ROLE_NAME_RE`、`_ANCHOR_COLON_RE` |
| `table_role_detector.py:22` | `_ROLE_COLUMN_HEADER_WORDS` + `_ROLE_COLUMN_EXCLUDED` / `_TBL_HDR_NONNAME` / `_TBL_HDR_EXCLUDE_ENDINGS` | 表头角色词 + 反向排除词 |
| `redact_word.py:1069` | `_TABLE_HEADER_COL_KEYWORDS`（12 词） | Word 专用表头词 |

**收敛建议**：抽到 `config.json` 单一可配置项 `name_anchor_words`，分三类：

- **角色类**（负责人/联系人/审批人/主讲/记录人…）—— 精度高，可单独触发；
- **名单类**（成员/组员/参会人员/名单/如下/包括…）—— **必须配合同构性 ≥2 项**才触发；
- **签名/落款类**（签字/盖章/特此通知…）—— 供 T3 使用。

**行业差异化的结论：不做按行业分表**（银行/政务/科技各一份），维护成本会爆炸，且形态判别本身已把行业业务词挡在门外。行业差异改为**可选叠加包**（默认只用通用表，特定场景再叠加），并保留现有 `_ROLE_COLUMN_EXCLUDED` 一类的**反向排除词**机制。

### 4.8 规则A 的最终定位与量化退出门槛（裁决点 5）

**规则A 定义**（`common_rules.py:1454`）：

```python
(?<![a-zA-Z0-9])(?:{复姓|单姓})[name_pool 字符类]{1,3}
```

即「姓 + 1~3 个名用字」的**全局形态粗筛**，不依赖任何上下文。

| | 优点 | 缺点 |
|---|---|---|
| D16 精确表 | 零误伤；名单内 100% 召回 | 覆盖率天花板（名单外人员漏） |
| **规则A** | **唯一能捞名单外人名的机制**（召回主力） | **笛卡尔积全局匹配 → 误伤无上界（实测 51.0%）** |

**裁决：保留在主链路，但降级为「区域外唯一兜底 + 置信分级」。**

- 区域内：不再走规则A，改用 L1 D16 / L2 同构；
- 区域外：规则A 仅在有弱上下文信号时启用，并按 #49 的 R2/R3 分级收紧（低危姓 + 2 名用字 / 高危姓 + 3 名用字）；
- **绝不整体退出**：实测纯区域化 + D16 召回仅 **6/12**，规则A 若全退将**漏脱 6 个真名**。漏脱是合规红线，误伤是可用性缺陷，二者不对称。

**量化退出门槛**（避免讨论空转，设明确验收条件）：

> 只有当 **N-C 区域 + D16 + L2 同构** 的召回 ≥ **12/12**，且 102 条通用语料误伤 ≤ **5%** 时，才允许把规则A 从主链路移除；达不到之前，规则A 始终保留在兜底位。

对应的实施节奏：区域化落地后**先观察一个版本**，用真实文档回归数据说话，再决定是否动规则A 的主链路地位。

## 六、风险与开放问题

| 风险 | 说明 | 缓解 |
|---|---|---|
| **区域漏检** | 名单没有分隔符（连续姓名）时区域化失效 | 退回 D16 + 分级规则A；区域化是**增益**不是**替代** |
| **区域过宽** | 锚点词后跟着长串业务词被误判为名单 | 要求候选同构（长度/形态一致）+ ≥2 项 |
| **占位符字母污染** | `name_pool` 含 15 个占位符字母，会使「张三ABC」被判为姓名 | 姓名形态判定要求**全为汉字**；M9 只清标点，不动字母 |
| **锚点词误判** | 「人员配备」「负责人制」等含锚点词但非名单 | 需候选同构性 + 形态双约束（实测已验证「需求包括、开发、测试、上线」零误伤） |
| **命名冲突** | 新层若沿用「N-B」会与 Issue #16 既有 N-B 冲突 | 新层定名 **N-C**；T2 明确为既有 N-B 的升级版而非新层（§4.1/§4.2） |
| **Word 合并单元格** | `w:gridSpan`/`w:vMerge` 导致列位错位，列级判定串列 | 补齐时按网格坐标还原真实列位（§4.6） |
| **性能** | 两阶段扫描增加一遍遍历 | 区域检测是线性扫描，正则预编译；预期 P95 增量 < 1ms（待 P1 实测） |
