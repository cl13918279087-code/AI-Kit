## 一、项目背景与目标

### 1.1 项目背景

在金融行业项目实施过程中，存在大量需要对外分享或提交监管的文档材料。这些材料（如核心系统迁移方案、演练操作指南、需求文档等）通常包含：

- **银行名称**：涉及信息披露边界
- **人员姓名**：涉及个人隐私保护（姓名、手机号、身份证号等）
- **日期信息**：涉及商业敏感时间节点
- **账号/金额**：涉及金融数据安全
- **地址/IP 等**：涉及基础设施信息

手动脱敏效率低、易遗漏，需要构建自动化工具。

### 1.2 项目目标

构建一套**可配置的、批量化的、带有质量保障**的金融文档脱敏工具，支持 Word / Excel / PPT / PDF / 图片五类文档格式，集成 LLM 智能识别提升未知敏感词的发现能力，并生成可审计的脱敏报告。

### 1.3 约束条件

- 不涉及银行系统应用层数据，仅处理项目文档材料
- 脱敏结果需支持人工复核（通过对照报告）
- 工具需在项目现场可用（Windows / macOS / Linux）
- 处理过程不对原始文件产生影响（输入/输出分离）

## 三、检测机制设计

### 3.1 三层混合检测

**Layer 1 — LLM 智能检测**

- 使用 MiniMax-Text-01，temperature=0.05（低随机性）
- 自动分段（6000 字符/chunk，200 字符重叠）
- 识别未知业务词汇（银行名、系统名、产品名等规则无法覆盖的实体）
- 低置信度项（<0.75）标记为待人工确认

**Layer 2 — Regex 规则兜底**

- 覆盖所有标准格式：日期、手机、身份证、银行卡、邮箱、IP、MAC
- **链式顺序替换**：长文本先处理，短文本后处理（防止短文本误伤长文本）
- 关键修复：日期范围保留连接符（`YYYY/MM/DD 至 YYYY/MM/DD`）

**Layer 3 — 角色词上下文**

- 通过角色词（`联系人：`、`总行支持人员：`等）发现文档中具体人员姓名
- 排除词表防止误脱（`项目组`、`总行`等通用术语）

### 3.2 规则优先级

```
邮箱 → IP/MAC → 地址 → 身份证 → 银行卡 → 手机/固话 → 
日期范围 → 日期 → 银行名 → 组织名 → 人员姓名
```

## 四、姓名检测规则详解（Rule A / Rule B）

### 4.1 规则体系

姓名检测由两条正则规则协同工作：

**Rule A — 姓氏 + 1-2 个名字汉字（通用场景）**

```
(?<![a-zA-Z0-9])
(?:{surname_pool})
[{name_pool}]{1,2}
(?![a-zA-Z0-9](?:行(?![a-zA-Z0-9\u4e00-\u9fa5])|[\u4e00-\u9fa5]))
```

- 左边界：非 ASCII/数字（防止单词内匹配）
- 姓氏池：200+ 常用姓氏
- 名字池：154 个名字常用汉字（不含 `行/为/业/务/支` 等常见中文字）
- 右边界：`(?!...)` 在 `行` 字后面跟非 ASCII/非汉字字符时阻止匹配（防止"支行/分行"被误当人名）；其他汉字后面跟汉字时也阻止（防止"史明/时不"等被误当人名）

**Rule B — 冒号后姓名（总行支持人员：XXX 等场景）**

```
(?<=[\u4e00-\u9fa5\uff1a])
(?:{surname_pool})
[{name_pool}]{2}
(?![a-zA-Z0-9])
```

- 左边界：CJK 字符或全角冒号 `\uff1a`（`：`）
- 固定 2 字名字（避免单字人名"安卓"等被误匹配）
- 全角冒号 `\uff1a` 显式加入（不在 CJK 区间内）

**Rule C — 冒号后姓氏+单字名（在特定角色词上下文中）**

```
(?<=：)
(?:{surname_pool})
[{name_pool}]{1}
(?![a-zA-Z0-9])
```

- 处理"组长：樊霖副组长"等场景——"组长："后紧跟 2 字姓名，但第 1 字是姓、第 2 字是名（霖）
- Rule B 要求恰好 2 个名字汉字，但"樊霖"只有 1 个名字汉字（霖），Rule B 无法匹配
- Rule C 放宽右边界：仅阻止 ASCII 字符跟随，允许 CJK 字符（如后面的"副"字）

### 4.2 name_pool 管理原则

`config.json` 中的 `name_pool` 必须遵循以下原则：

| 字 | 是否在 name_pool | 原因 |
|----|----------------|------|
| `行` | ✓ | "毛航行"等人名需要，但 Rule A 右边界已防护 |
| `为` | ✗ | "应为/预计为"会被误当人名 |
| `业` | ✗ | "业务/提高业务"会被误切为"高务" |
| `务` | ✗ | 常见词，不应作为人名 |
| `支` | ✗ | "支行"会被误当人名（支是姓氏） |
| `不` | ✓ | 正常名字用字 |
| `明` | ✓ | 正常名字用字 |
| `史` | ✓（在姓氏池）| 正常姓氏 |

### 4.3 Post-processing 误脱敏纠正

正则无法覆盖所有边界情况，通过后处理纠正已知误脱敏词对：

```python
post_fixes = [
    ('清XXX下', '清单如下'),
    ('营运XXX部', '营运计财部'),
    ('XXX务部', '计财财务部'),
]
```

### 4.4 分支行后缀保留

`_branch_repl` 函数保留 `分行/支行/营业部/网点` 后缀：

```python
def _branch_repl(m):
    suffix = m.group(1)   # 行 / 分行 / 支行 / 营业部 / 网点
    return f'XX{suffix}'  # → XX分行 / XX支行 / XX营业部
```

### 4.5 DATE 后处理

DATE pattern 将日期替换为 `YYYY年MM月DD日`，但紧跟在"应为/必须为/须于"后的日期需用 `XXXX年XX月XX日` 替代（避免"应为YYYY年"这样的明显误脱敏）：

```python
_prefixes = ('应为', '必须为', '须于')
# 扫描所有 'YYYY年MM月DD日'，若前3字在前缀表中，替换为 XXXX年XX月XX日
```

## 五、各格式处理方案

### 5.1 Word（.docx / .doc）

**处理策略：**
- `lxml + zipfile` 直接读写 OOXML 内部 XML
- 完全绕开 python-docx 的高层保存逻辑（会合并 runs 导致格式丢失）
- 逐 `<w:t>` 节点替换，保留所有样式（标题/表格/页眉/页脚/批注）

**处理范围：**
- 正文段落、表格单元格
- 页眉、页脚
- 文本框（`wps:txbx`）
- 批注（`comments.xml`）
- 文档属性（`docProps/core.xml`）
- 嵌入图片文件名（含银行 Logo 关键词的图片替换为纯黑图）

**`.doc` 处理：**
- 通过 LibreOffice 转换为 `.docx` 后处理
- 转换失败时保留原文件（不破坏输入）

### 5.2 Excel（.xlsx / .xls）

**处理策略：**
- OOXML 直写（`xl/sharedStrings.xml` / `xl/worksheets/*.xml`）
- `.xls` 使用 `xlrd` 读取 + `xlwt` 写入

**处理范围：**
- 共享字符串表（Excel 最常用文本存储）
- 工作表单元格内联文本
- 批注
- 页眉页脚
- 文档属性

### 5.3 PPT（.pptx / .ppt）

**处理策略：**
- OOXML 直写（`ppt/slides/*.xml`）
- 媒体文件名脱敏（重命名含敏感词的图片/音视频）
- `.ppt` 通过 LibreOffice 转换

**处理范围：**
- 幻灯片正文（形状/文本框/表格）
- 幻灯片布局、母版
- 演讲者备注
- 媒体文件名（银行 Logo 检测）

### 5.4 PDF

**文本型 PDF：**
- PyMuPDF 提取带坐标文本（`page.get_text("dict")`）
- 在原位置绘制黑色矩形遮盖
- 在遮盖区域写入脱敏占位符（灰色小字）

**扫描版 PDF：**
- PyMuPDF 300 DPI 渲染为图片
- pytesseract OCR（含坐标的马赛克遮盖）
- OpenCV 启发式 Logo 检测（颜色方差 + 边缘密度）

### 5.5 图片

- pytesseract OCR 定位文字及坐标
- 正则识别敏感信息 → 马赛克/模糊/黑块遮盖（可配置）
- 银行 Logo 检测（OCR 找到"银行"→ 扩展左侧区域 → 颜色/边缘特征判断）

## 六、LLM 集成方案

### 6.1 部署形态与模型接入

本项目是 **Agent 技能包**：LLM 调用能力由 Agent 侧承载（见 `SKILL.md` 第五节-A「AI Agent 直接处理模式」，无需任何第三方 API Key）。脚本侧的 `llm_client.py` / `redact_llm.py` 是**可选的直连通道**，仅在需要独立推理网关时启用。

> **合规基线**：agent 与 LLM 均部署于**企业内网**。因此脚本侧直连通道必须指向内网推理网关，不设公网默认值、不做隐式外发。

| 接入方式 | 说明 | 是否需 API Key |
|----------|------|---------------|
| Agent 直接处理（推荐） | 复用 Agent 自身 LLM 能力，Agent 侧执行预脱敏后送入 | 否 |
| 内网推理网关 | 脚本侧直连内网网关，需配置 `base_url` + `allowed_hosts` | 是（内网网关密钥） |
| 公网 SaaS 直连 | **已不支持**：`base_url` 无公网默认值，且出网守卫默认拒绝 | — |

所有 OpenAI 兼容内网网关统一使用 `provider: "openai-compatible"`（默认值），`base_url` 需带 `/v1` 后缀。

### 6.2 内网推理网关配置

> ⚠️ **重要**：`llm_client.py` 的 HTTP timeout 控制在 `config.json` 的 `timeout` 字段，**不是** `openclaw.json` 的 `timeoutSeconds`。两者独立，前者控制 LLM 请求超时，后者控制 OpenClaw 桌面应用本身的超时。

```json
{
  "llm": {
    "enabled": true,
    "provider": "openai-compatible",
    "model": "内网推理网关模型名",
    "base_url": "http://llm-gateway.intranet.corp/v1",
    "api_key": "***",
    "allowed_hosts": ["llm-gateway.intranet.corp"],
    "require_private_network": true,
    "timeout": 300,
    "max_retries": 3,
    "pre_redact_before_llm": true
  }
}
```

**字段说明**

| 字段 | 默认 | 作用 |
|------|------|------|
| `enabled` | `false` | LLM 通道总开关，缺省关闭 |
| `base_url` | `""` | 推理网关地址，**无公网默认值**；为空即视为未配置，通道不可用 |
| `allowed_hosts` | `[]` | 出网白名单（精确主机名或后缀匹配），与内网地址判定二选一放行 |
| `require_private_network` | `true` | 是否允许私网/内网主机名直接放行 |
| `pre_redact_before_llm` | `true` | 送 LLM 前是否做最小化预脱敏（等长掩码） |

**出网守卫**：`scripts/llm_egress.py` 的 `check_egress()` 判定顺序为
① 命中 `allowed_hosts` → 放行；② 命中内网地址（私网 IP / `*.local|.internal|.intranet|.lan|.corp|.intra` / `localhost`）→ 放行；③ 其余一律拒绝并降级纯规则。
拒绝原因只回显端点与规则名，**不含任何文档原文**。

### 6.3 送 LLM 前的最小化预脱敏

`scripts/entity_detector.py` 的 `pre_redact_for_llm()` 在文本送入 LLM **之前**，对个人唯一标识做**等长掩码**（全角 `Ｘ` 逐字符替换）：

- **唯一标识**：身份证号、银行卡号、手机号、固话、邮箱
- **准唯一标识**：银行账号与卡号（可带空格分组）、证件号码（护照 / 通行证 / 社保 / 公积金）、住址（**关键词前缀限定**：住址 / 通讯地址 / 户籍地址 …）
- **敏感载体**：证件影像引用（正反面 / 扫描件 / 复印件 / 照片 + 图片扩展名）
- **不覆盖**：银行名、日期、金额、机构行址（LLM 判「角色词 + 姓名」所需上下文，且由规则层确定性脱敏）
- **等长的意义**：LLM 返回的 `start`/`end` 偏移量完全保持原义，命中结果可直接回写原文
- **上下文标签保留**：账号 / 证件号 / 住址采用「命名组掩码」——只遮蔽数值部分，
  「账号：」「地址：」等标签保留，既满足最小化又不破坏 LLM 的语义理解
- 掩码段若被 LLM 误识别为实体，直接丢弃（`_is_masked_only`）

CLI 入口：`scripts/llm_premask.py`（Agent 直处理模式与脚本侧共用同一套掩码实现）。

### 6.3.1 Agent 直处理模式的端点合规自检

脚本侧出网守卫只管得住**脚本自带**的 LLM 客户端通道；Agent 直处理模式的端点由
Agent 侧配置，**不在仓库守卫管辖内**。为此提供 `scripts/endpoint_check.py`：

```bash
python3 scripts/endpoint_check.py --base-url http://llm-gateway.intranet.corp/v1
```

- **只读、不发任何网络请求**，复用 `llm_egress.check_egress()`，保证自检口径与
  实际守卫口径永不漂移；
- 退出码：`0` 全部合规 / `2` 存在不合规端点 / `3` 参数或配置错误；
- `--json` 输出供内网合规扫描与流水线调用；
- SKILL.md 第五节-A 新增 **Step 0 · LLM 端点合规自检（内网部署必做）**。

`SKILL.md` 第五节-A 的 Agent 直处理模式执行同一套掩码（`scripts/llm_premask.py` CLI 或等价逻辑），确保「先掩码、后送 LLM」。

### 6.4 LLM 使用策略

- **仅用于补充**：Regex 能覆盖的格式不用 LLM（节省 token、降低延迟）
- **低 temperature**：0.05，减少随机性，提高一致性
- **JSON Mode**：指定 `response_format: json_object`，减少解析错误
- **分段处理**：6000 字符/chunk，200 字符重叠，防止边界漏检
- **错误降级**：LLM 调用失败或被出网策略阻断时记录警告，继续用 Regex 层兜底，不中断处理
- **可审计**：每次运行在 manifest 的 `llm_audit` 段留痕（`enabled` / `chars_sent` / `pre_redacted` / `masked_chars` / `masked_spans` / `egress_policy`）

## 七、批量处理与断点续传

### 7.1 批量并行

- 使用 `ProcessPoolExecutor`，默认 5 并行（可配置）
- 每个子进程独立处理一个文件，结果通过 Future 返回
- 主进程负责任务分发、进度更新、报告生成

### 7.2 断点续传

- 状态文件 `.redact_state.json` 记录已处理文件列表
- 中断后重新运行 `--resume`，自动跳过已完成文件
- 支持增量：新增文件只处理新增部分

### 7.3 进度展示

- `tqdm` 进度条：`{已完成}/{总数} [已用时间<剩余时间]`
- 实时显示成功/失败计数

## 八、质量保障

### 8.1 残留敏感词自检

脱敏完成后，对输出文件进行二次扫描，确认无残留：

```python
def residual_scan(text: str) -> List[str]:
    """扫描脱敏后文本中是否还有未处理的敏感信息"""
    patterns = [...]  # 关键正则
    residual = []
    for pattern, _ in patterns:
        matches = pattern.findall(text)
        residual.extend(matches)
    return residual
```

### 8.2 误脱检测

- LLM 二次验证：给定原始+脱敏文本对，检测误脱和漏脱
- 关键字段（身份证、银行卡）双重确认

### 8.3 对照报告

- JSON 格式：原始值 → 脱敏值完整对照
- Markdown 格式：可读性摘要报告（人读）
- 支持人工复核后导出存档

### 8.4 降级台账与审计链（产物失真的可见性）

「降级但产物仍生成」是典型的**静默失真**：`.doc` → `.docx` 的三级转换链中，
antiword 级会**丢失全部格式与表格结构**，产出物看似脱敏完成、实则内容残缺。
`scripts/degradation.py` 统一登记此类事件，并在审计链三处同时呈现。

| 级别 | 含义 | 典型场景 |
|------|------|---------|
| `info` | 可选能力缺失，不影响产物完整性 | LLM 未启用（默认口径，不登记） |
| `warn` | 产物完成但**保真度下降** | textutil 转换、局部图片/嵌入对象需人工复核 |
| `critical` | 产物**内容可能失真或缺失**，必须人工复核 | antiword 转换丢失表格结构、PPT 无转换器直接复制原文件 |

| 呈现位置 | 实现 |
|---------|------|
| manifest | `scripts/manifest.py` → `degradations` 段（`count` + `items`）+ Markdown「⚠️ 降级产物」章节 |
| 批量报告 | `scripts/pipeline.py` → `RedactResult.degradations` + 报告「⚠️ 降级产物清单（需人工复核）」章节 |
| 退出码 | `scripts/redact_all.py` → `0` 无降级 / `2` 有降级产物 |

**退出码全口径**：`0` 全部成功且无降级；`1` 存在**失败**文件（无产物）；
`2` 无失败但存在降级产物（须人工复核）。**失败优先于降级**——失败意味着「没有产物」，
降级意味着「有次品」，二者不可混为一谈，否则失败会被降级掩盖。

**跨进程约束**：批量处理使用 `ProcessPoolExecutor`（spawn），降级台账是**进程内**状态，
因此必须在**子进程内、处理刚结束时**读取，再随 `RedactResult` 回传父进程汇总。

> 台账登记内容**只含组件名、级别、原因与复核提示**，不含任何文档原文，可直接归档。

### 8.5 CI 门禁

`.github/workflows/ci.yml` 提供三层强制卡口（`push` / `pull_request` on `main`）：

| 层 | 内容 |
|----|------|
| `lint` | `compileall` 语法编译 + 全仓 JSON 合法性校验 |
| `unit` | `pytest tests/`（先不含 benchmark，再完整） |
| `gate` | `python scripts/bench_metrics.py` — **八项指标门禁，唯一阈值源** |

门禁阈值全部取自 `scripts/bench_metrics.py`（与 `quality_validator.py` 同源），
workflow 内**不硬编码任何阈值数字**，避免两处口径漂移。`gate` 的 `--json` 报告
以 artifact 形式存档，供审计追溯。

## 十三、已知问题与解决记录

### 13.1 Issue 3：误脱敏（已修复）

**问题**：中文常用词被姓名正则误匹配，如"提高业务品种"→"提XXX务品种"。

**根因**：`name_pool` 包含了 `行/为/业/务/支` 等常见中文字，Rule A 右边界不完善导致机构名被误切。

**修复措施**：
1. 从 `name_pool` 移除 `为/业/务/支`（`行` 保留，因"毛航行"需要）
2. Rule A 右边界精确化：`(?![a-zA-Z0-9](?:行(?![a-zA-Z0-9\u4e00-\u9fa5])|[\u4e00-\u9fa5]))`
   - `行` 后面跟 CJK 非标点字符时阻止匹配（防止"支行/分行/总行"）
   - 汉字后面跟汉字时也阻止匹配（防止"史明/时不"）
3. Post-processing 还原已知误切：`XXX执`+`行`→`执行`，`XXX细`+`历`→`明细`，`XXX行`+`可/人`→`行`

**遗留**：源文件与标准版存在结构差异（.doc → .docx 转换后节点粒度不同），部分段落级对齐有偏差。

### 13.2 Issue 4：漏检（已修复）

**问题**："总行支持人员：汪晶晶"等场景中，姓名在冒号后但不在 Rule A 左边界范围内。

**修复措施**：
1. Rule B 左边界显式加入全角冒号 `\uff1a`：`(?<=[\u4e00-\u9fa5\uff1a])`
2. Rule B 固定 2 字名字，避免单字人名"安卓"等误匹配

### 13.3 Issue：DATE pattern 误替换"应为2022年3月31日"

**问题**：DATE pattern 将"应为2022年3月31日"中的日期替换为"YYYY年MM月DD日"，造成"应为YYYY年MM月DD日"的明显误脱敏。

**修复措施**：Post-processing 检测紧跟在"应为/必须为/须于"后的 `YYYY年MM月DD日`，替换为 `XXXX年XX月XX日`。

### 13.4 Issue：LLM timeout 控制路径

**问题**：`llm_client.py` HTTP timeout 实际由 `config.json` 的 `timeout` 控制，而非 `openclaw.json` 的 `timeoutSeconds`（两者独立）。

**修复措施**：`config.json` 中 `timeout` 字段设为 300 秒。

### 13.5 Issue：Word XML 腐败（w:t节点文本堆积，第一个run的w:t包含所有文本）

**问题**：`redact_word.py` 中 `_process_word_xml_with_llm` 处理后，部分 docx 文件的段落中第一个 run 的 w:t 节点包含所有文本（多节点内容堆积到第一个 w:t），导致后续文本丢失或重复。

**根因**：存在两个连锁 bug：
1. **双加工问题**：LLM步骤（`apply_spans_to_nodes`）修改了 w:t 节点后，regex步骤在同节点上再次调用 `apply_redactions()` 并重新分配文本到 w:t，导致文本在多个 w:t 节点间重新分配时位置错位
2. **多t节点文本只写ts[0]**：旧代码只将 `ts[0].text = redacted` 后清空其余节点，当同一run内有多个 w:t 节点时，所有文本堆积到第一个节点

**修复措施**：
1. 新增 `llm_modified_nodes` 集合追踪LLM已修改的节点，regex步骤跳过已处理节点
2. 新增 `_redistribute_text_nodes()` 函数，将redacted文本按原始长度比例正确分配到所有 w:t 节点
3. 同步修复 `_process_word_xml` 中的相同文本分配bug

**验证方法**：脱敏后 docx 文件中 `w:t` 节点数量应与原始文件一致，内容正确分布。

### 13.6 Issue：Group3 DOC 文件比对 0% 重叠

**问题**：DOC 文件（.doc）脱敏后与标准版比对，重叠率为 0%。

**根因**：`extract_doc_texts` 直接对二进制 OLE2 格式的 DOC 文件做 UTF-16-LE 解码，产生乱码，导致比对结果完全不可信。

**修复措施**：重写 `extract_doc_texts()` —— 先用 LibreOffice 将 DOC 转换为 DOCX，再用 `extract_docx_texts()` 提取可靠文本。降级方案：转换失败时回退到原始基础解码。

### 13.7 Issue：XXX 位置比对过于脆弱（大量假阳性误判）

**问题**：`extract_xxx_regions` 使用精确字符位置匹配（`set` 集合），当 LibreOffice 转换导致文本结构略有变化时，XXX 位置偏移导致大量假阳性误判。

**修复措施**：新增 `xxx_context_signatures()` 函数，为每个 XXX 区域提取前后各5字符的上下文签名 `[前5]XXX[后5]`，使用上下文签名做模糊重叠匹配，而非精确位置。对 DOC 转换等导致的文本结构微小变化更鲁棒。
