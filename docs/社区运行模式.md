# 文档脱敏项目社区运行模式（v1.0）

> 生效日期：2026-09-11
> 代码仓：https://github.com/cl13918279087-code/AI-Kit（main 分支）
> 维护者：AI探索（WorkBuddy 维护工作台）
> 适用对象：所有建立独立 WorkBuddy 操作环境、运行文档脱敏项目的小组成员及其 AI 助手

---

## 一、定位

社区的目标不是"多人写代码"，而是**分布式使用 → 结构化反馈 → 统一评估整改**的循环：

- 每个成员在独立环境中**真实使用**技能包（真实项目文档是唯一的试金石）
- 发现的问题和改进以**标准化清单**回传，而非直接改代码
- 维护者统一评估、整改、发布，保证 main 始终是唯一可信版本

这一模式已在 2026-09 的实践中完整跑通（redact_docx_v2 改进项清单 → 评估意见 → R1-R7 整改，commit bddc90b），本文件将其固化为常态机制。

## 二、角色与职责

| 角色 | 承担者 | 职责 |
|---|---|---|
| **维护者** | AI探索（维护工作台） | 评估改进清单、执行整改、评审 PR、版本发布、安装版同步、回答使用问题 |
| **贡献者** | 各小组成员 + 其 AI 助手 | 真实使用技能包、记录问题、按模板提交改进项清单、验证发布版本 |
| **合规审核人** | 成员中的业务负责人（人工） | 红线事件裁决、对外回传内容审批、涉及客户名/敏感词字典的决策 |

维护者承诺：改进项清单在接收后 **48 小时内**给出《评估意见》。

## 三、仓库与分支模型

```
main            ← 唯一真源，始终可发布（受保护）
└── feature/*   ← 较大改动（R4 姓名重构类）先开分支评审
tags: v1.x.y    ← 每次发布打 tag
```

- **贡献者不得直接 push main**。反馈走第五章流程；确有代码贡献的，push 到 `feature/<主题>` 分支由维护者评审合入
- **main 的变更只能来自**：维护者整改提交、或经评审的 feature 分支合并
- 历史教训：多机器人直接推 main 曾造成文件互相覆盖（extract_text_from_xml 修复丢失事件），分支保护是硬约束

## 四、核心原则：只改一处，杜绝副本漂移

项目曾因 4 份代码副本漂移付出大量清理成本（P0-P2 治理）。铁律：

1. **main 是唯一真源**。成员环境只有两类副本：
   - **运行副本**：`~/.workbuddy/skills/doc-redact/`（安装版，只读，用同步命令更新，不手改）
   - **开发副本**：`git clone` 的工作区（改代码在这里，改完走流程回传）
2. 本地实验性改动**不覆盖技能包原版文件**（v2 清单的正确做法：另存 `_v2.py` 出 diff）
3. 同步安装版命令（成员环境固定使用）：

```bash
rsync -av --delete \
  --exclude '工作目录/' --exclude 'docs/' --exclude 'output/' \
  --exclude '共建项目/' --exclude '.git*/' --exclude '.workbuddy/' \
  --exclude '.gitignore' --exclude 'README.md' \
  <你的clone目录>/ ~/.workbuddy/skills/doc-redact/
```

## 五、贡献流程（标准闭环）

```
使用 → 发现 → 本地改进+实测 → 提交改进项清单 → 维护者评估 → 整改/PR → 回归验证 → 发布 → 贡献者验证
```

**第 1 步：发现问题**。使用中记录异常（误伤/漏脱敏/格式破坏/崩溃），保留原始文档与输出文档（本地留存，勿入库）。

**第 2 步：本地改进与实测**（可选但强烈建议）。针对问题做改进版，并用真实文档跑出对比数据。不采信"感觉有误伤"，必须给出可复现样例。

**第 3 步：提交《改进项清单》**（模板见附录 A），提交方式（按优先级）：
- GitHub Issue（模板已配置：缺陷报告 / 改进建议，均含**提交者署名**必填项）
- 或直接将清单文档放入 PR / 发给维护者

**提交者署名规则**：
1. 所有 Issue / PR / 清单文档**必须署名**——多成员共用同一 GitHub 账号发布时，署名是区分真实贡献者的唯一依据
2. 署名格式：真实姓名（建议），或个人 GitHub 用户名；机器人代发时由机器人代填成员署名，不得省略
3. 维护者在评估意见、整改 commit（`响应 Issue #N，贡献者：X某某`）、CHANGELOG 及贡献档案中回溯标注署名，确保贡献可归属
4. 未署名的提交，维护者先在 Issue 中向提交方（群内）确认归属后再进入评估流程

**第 4 步：维护者评估**。逐条在当前 main 上**实测复现**清单指控，输出《评估意见》（模板见附录 B）：属实 / 部分过时 / 已过时 / 需扩大范围，并给出 R# 编号整改清单（P0 合规风险 / P1 结构改进 / P2 优化）。

**第 5 步：整改执行**。维护者按 R# 顺序整改；每项整改必须通过第六章质量门禁。

**第 6 步：发布与回传**。commit + push + tag（第七章），同步安装版，向清单编制方回传评估结论与整改结果。

## 六、质量门禁（合并硬条件，缺一不合并）

| # | 门禁 | 验证方式 |
|---|---|---|
| G1 | 实测复现 | 每项指控/修复在当前 main 上跑样例，不采信口头描述 |
| G2 | 红线检查 | 脱敏输出中客户名/人名/银行名零残留（硬搜索敏感词清单） |
| G3 | 回归基线不劣化 | 6 组比对基线（漏检/误检数）不高于现有水平；有意调整口径需在评估意见中说明 |
| G4 | 常用词回归 | 姓名误伤测试集（说明书/实施方案/骨干成员等 8+ 例）保持通过 |
| G5 | 端到端验证 | 至少 1 个真实 docx/doc/xlsx/pptx 全流程跑通 |
| G6 | 敏感物不入库 | 提交内容不含客户文档；清单样例已脱敏（gitignore + 提交前人工确认） |

PMO 0/3 · 差异分析 5/7 · UAT3 2/6 · 郑州pptx 13/7 · 尖刀内容 1/45 · 福建 56/149*
（*含提取通道序列化差异，评估时以维护者复核为准）

## 七、版本与发布

语义化版本（semver）：
- **patch**（v1.2.2）：误伤词表扩充、单点 bug 修复
- **minor**（v1.3.0）：新文件格式支持、新规则通道、占位符口径调整
- **major**（v2.0.0）：规则引擎架构变更（如姓名规则重构 R4）

每次发布：
1. 更新 `CHANGELOG.md`（版本号 + 日期 + 改动列表 + 关联清单编号）
2. commit + push + `git tag vX.Y.Z`
3. rsync 同步安装版技能包
4. 在群内发布变更公告（一句话说明成员需要做什么：通常为"同步安装版"）

## 八、安全与合规红线

1. **客户文档永不入库**：`工作目录/`、`output/`、客户目录已在 .gitignore；提交前 `git status` 人工确认
2. **改进项清单中的样例必须先脱敏**：引用真实文档内容时，替换客户名/人名后再提交（可参考"XX银行/张某某"写法）
3. **银行名白名单（config.json bank_names）涉及服务客户名单**，新增客户银行名须合规审核人批准
4. **验证用真实文档在成员本地留存**，评估所需的复现样例以"最小可复现片段"形式提交

## 九、AI 机器人协同纪律

成员环境的 AI 助手（机器人）是主要操作者，须遵守：

1. **拉取前保护现场**：本地有未提交改动时，先 `git stash` → pull → `stash pop`，禁止直接 reset 丢弃
2. **提交规范**：`<type>: <一句话摘要>` + 正文列改动点，type ∈ fix/feat/refactor/docs/chore
3. **不采信缓存**：Edit 工具报成功后，对关键修改用 grep 复核落盘（文件可能被外部进程覆盖）
4. **机器人改代码须附验证证据**：复现样例 + 回归结果，写进 commit message
5. **跨环境上下文交接**：机器人依赖的工作记录放 `.workbuddy/memory/`（不入库），对外交接信息一律写在 issue/PR/清单文档中
