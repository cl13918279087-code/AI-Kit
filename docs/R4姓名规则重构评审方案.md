## 一、背景与动机

### 1.1 现状：补丁叠加已逼近维护极限

自 v1.3.0 以来，姓名规则通道累计叠加了 **19 项规则（R-①~R-⑲）**，其中直接围绕"姓名误伤/漏检"的守卫类补丁已达 9 处：

| 补丁 | 机制 | 引入背景 |
|---|---|---|
| EXCLUDED_COMMON_WORDS（87行） | 常用词黑名单，命中即放弃替换 | Rule A 右边界放宽误伤 |
| _COMMON_BIGRAMS 二字词保护 | 常用二字词不拆 | 二字姓名误伤 |
| _name_guard_sub_counted 应用层过滤 | 替换前查上下文 | "说明书→说XXX" |
| post_fixes 硬编码恢复表（1160行） | 错误输出→正确输出的字面回写 | 历史误伤个案 |
| XX 恢复段（1175行） | 姓氏+XX+名字单字 → XXX | 地址通道截断姓名（黄日镇） |
| R-⑱ 机构后缀守卫（1187行） | XX 后机构后缀开头则跳过合并 | Issue #14 关XXX行 |
| R-⑲ 「成立」黑名单 | 同上 | Issue #14 附带发现 |
| R-③ 日期残字符修复 | 正则边界修正 | \2 残字符 |
| R-⑥⑨ 池剔除（备/银） | 逐字足迹评估后剔字 | 误伤换漏检的取舍 |

### 1.2 结构性问题（以 Issue #14 为标本）

Issue #14 暴露的不是单点缺陷，而是**字符池正则法的结构性局限**：

1. **"先误伤、后恢复"的倒置逻辑**：规则先产生错误输出（XX银行），再由恢复段猜测修复（XX→XXX），每次修复又引入新误伤面（中心/学校），再打新补丁（R-⑱）——循环无收敛保证；
2. **替换决策与字符池强耦合**：`于银行` 是否是姓名，取决于「银」是否在 name_pool——池的任何增删都在"漏检风险 ↔ 误伤风险"间滑动，R-⑥/R-⑨/R-⑰ 三次剔字均需全量足迹评估；
3. **无语言学边界概念**：正则不知道「说明书」是一个词、「孙海刚行长」里"行长"是职位——所有常识只能以字面补丁形式注入。

### 1.3 重构目标

- 误伤（过遮盖）显著下降，post_fixes 硬编码表清零；
- 漏检不劣于现状（基线 1361 处命中零消失为硬门禁）；
- 新增误伤场景时**通过配置/词典扩展**而非代码补丁解决；
- 对外 API（`apply_redactions` / `apply_redactions_counted` / config.json schema）**零破坏**。

## 二、目标架构：四层候选-校验流水线

核心转变：**从"正则直接替换"改为"候选生成 → 逐层校验 → 确认替换"**。

```
文本 ──► L1 候选层（现有正则池，只标span不改文）
          │  输出：候选span列表 [(start, end, category, score0)]
          ▼
        L2 分词边界校验层
          │  候选span与分词结果冲突（跨词/含常用词）→ 剔除或降级
          ▼
        L3 上下文通道
          │  角色词/机构后缀/地址成分/称谓 等特征评分，低分剔除
          ▼
        L4 LLM 兜底层（可选，默认关闭）
          │  仅处理 L3 之后的争议候选；本地模型优先
          ▼
        确认替换（占位符统一走现有 replacement 映射）
```

### L1 候选层
- **完全复用现有正则**（_build_patterns 不动），但 `_counting_sub` 改为输出候选 span，不直接改写文本；
- 收益：地址通道、电话通道、姓名通道产生的"中间态误替换"（XX银行→关XXX行链条）整体消失——恢复段、机构后缀守卫、post_fixes 表在架构上不再需要。

### L2 分词边界校验层
- 引入分词器对原文分词，候选 span 若与词边界冲突则剔除；
- **开放问题 A（评审重点）**：分词器选型——
  - 方案 a：jieba（成熟，但引入第三方依赖，与 R5 的 RapidOCR 依赖决策可合并考虑）；
  - 方案 b：自建精简词典 + 最长匹配（零依赖，覆盖度受限，可用 EXCLUDED_COMMON_WORDS 迁移为词典条目起步）；
  - 建议：**b 起步、a 可选**（try-import 降级），保持"零依赖可运行"的安装版底线。

### L3 上下文通道
- 特征化现有所有散落的守卫：角色词表（_ROLE_KEYWORDS）、称谓（先生/女士/总/经理）、机构后缀表（R-⑱ 的 13 项）、地址成分表；
- 输出为**评分**而非硬规则：如"候选后有称谓 → 加分；候选与机构后缀重叠 → 减分"；
- 现有 EXCLUDED_COMMON_WORDS / _COMMON_BIGRAMS 全部迁移为词典数据，代码中不再有字面词表。

### L4 LLM 兜底层（默认关闭）
- 仅对 L3 后评分处于灰区的候选调用；
- **隐私红线（评审重点）**：脱敏文本本身即敏感数据，**禁止云端 LLM**——仅限本地模型（如 Ollama）或干脆不启用；
- **开放问题 B**：是否值得保留此层？社区语料规模下 L2+L3 可能已足够，L4 或延后至独立评审。

## 三、分阶段实施计划（每阶段独立可回滚、独立过门禁）

| 阶段 | 内容 | 行为变化 | 门禁 |
|---|---|---|---|
| R4-a | 候选化重构：L1 输出 span，统一确认替换点；删除 post_fixes 与恢复段中"先错后修"链条 | 零（基线逐字节对比一致） | 基线 1361 处逐字节 diff = 0 |
| R4-b | L2 分词边界层（自建词典起步） | 消除二字词误伤类补丁 | 矩阵+姓名回归+误伤样例库全过 |
| R4-c | L3 上下文评分通道 | 守卫数据化，代码词表清零 | 同上 + 新增样例只改配置可修复验证 |
| R4-d | （可选）L4 本地 LLM 兜底 | 仅显式开启 | 独立评审 |

配套建设：
- **误伤/漏检样例库**（`工作目录/样例库/`）：历次 Issue 的复现样例沉淀为可执行回归集（`pytest` 化），当前 14 个 Issue 已有 60+ 断言样例；
- 性能预算：单页 docx 处理耗时增幅 ≤30%（jieba 分词约 +50ms/千字，可接受）。

## 四、风险与回滚

| 风险 | 缓解 |
|---|---|
| L2 分词词典覆盖不足致新漏检 | 基线零消失硬门禁 + 样例库回归；词典未覆盖场景退回 L1 现行为 |
| 候选化重构引入顺序回归（多规则重叠 span） | R4-a 要求与 v1.3.8 输出逐字节一致，diff 工具先行 |
| 依赖引入破坏安装版离线特性 | 分词器 try-import 降级，零依赖路径保底 |
| 版本跨度大（v1.3.8→v2.0.0） | 分阶段合入，R4-a 可先行以 patch 号发布（行为零变化），架构变更集中在 R4-b/c |

## 五、评审问题清单（请社区成员重点反馈）

1. **分词器选型**：自建词典（零依赖）vs jieba（可选依赖）？还是两者兼有？
2. **L4 是否保留**：本地 LLM 兜底的价值与维护成本是否匹配？
3. **样例库共建**：各成员业务语料中还有哪些高频误伤/漏检场景需要入样例库？（脱敏后样例即可）
4. **性能预算**：30% 耗时增幅是否可接受？有无超大文档场景需要压测？
5. **兼容性**：是否有成员在脚本中直接调用了 `_build_patterns` / `post_fixes` 等内部接口？（将标记为私有并迁移）
