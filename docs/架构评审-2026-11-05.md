# 全局架构评审报告（银行系统建设架构师视角）

> 评审日期：2026-11-05
> 评审范围：`scripts/`（28 个模块 / 19 817 行）、`tests/`（21 个测试文件）、`scripts/config.json`（约 11 万词条）
> 基线：`main@77c2c70`
> 评审方法：静态代码勘察 + 实测复现（构造最小样本执行真实代码路径）
> 评审立场：**面向银行内部合规审查与生产投产**的标准，不以「能跑通」为验收线

## 〇、总体结论

| 维度 | 评价 | 说明 |
|---|---|---|
| 规则层工程质量 | **优秀** | 双层 D16、区域优先、证据收窄、八项门禁、14.7 万区间零差异等价性验证——规则设计水平高于多数商业产品 |
| 工程化成熟度 | **偏弱** | 无打包、无 CI 流水线、无锁文件、`_build_patterns` 单函数 1498 行、19 个模块零测试 |
| 生产可用性 | **不合格（当前形态）** | 批量主链路存在**实测可复现的致命缺陷**，审计报表统计归零 |
| 银行合规适配 | **部分达标** | 已有裁决留痕与幂等设计；但缺密级分级、缺残留门禁、降级标记未进审计链 |

**一句话结论**：规则内核已达到可投产水位，但**工程外壳与审计外壳落后于内核 2～3 个数量级**。
若现在直接投产，最可能的事故不是「脱敏漏了」，而是「脱敏成功了但台账显示零成功」——后者在银行审计中性质更严重。

## 一、P0 阻断项（实测复现，必须在投产前修复）

### P0-1 批量主链路状态值不一致 → 审计报表统计归零

**实测证据**（`.workbuddy/tmp/verify_pipeline.py`，构造最小 docx 走真实 `batch_process`）：

```
返回状态集合: {'complete'}
报告输出:
  **处理文件数**: 1 | **成功**: 0 | **失败**: 0 | **跳过**: 0
```

**根因**：`process_single_file()` 产出的 `status` 是 `"complete"`（`scripts/pipeline.py:236` 等 4 处），
而**全部消费方**判定的是 `"success"`：

| 消费方 | 位置 | 后果 |
|---|---|---|
| 断点续传 `mark_done` | `pipeline.py:339` | 成功文件**永不入 done**，`--resume` 形同虚设 |
| 断点续传 `mark_failed` | `pipeline.py:341` | 失败判定正常，成功判定失效 |
| 进度条计数 | `pipeline.py:347` | 进度条永远显示 ✅0 |
| Markdown 报告三分类 | `pipeline.py:359-361, 392` | 成功/失败/跳过**三项全为 0** |
| 报告「按文件类型统计」 | `pipeline.py:369` | 整表为空 |
| 敏感项总数 | `pipeline.py:364` | `total_entities` 恒为 0 |

**银行影响**：批量脱敏台账（处理多少份、成功多少份、检出多少敏感项）**全部失真**。
监管检查、审计留痕、内控评价所依赖的正是这份报表。这不是统计口径瑕疵，是审计证据链断裂。

**修复建议**：定义 `RedactResult.Status` 枚举（`SUCCESS/COMPLETE/FAILED/SKIPPED/PENDING`），
统一为一个真值源；所有消费方引用枚举而非字符串字面量。**必须补 `tests/test_pipeline_*.py`**——当前 `pipeline.py` 零测试，这正是该缺陷能存活的直接原因。

### P0-2 批量处理不创建输出目录 → 首次运行必然全量失败

**实测证据**：
```
error = "FileNotFoundError: ... /out/a_脱敏.docx.tmp"
```

`process_single_file()` 直接向 `output_dir` 写入 `.tmp`，但**从不 `mkdir`**。
`redact_all.py` 单文件路径有兜底（`Path.with_name`），`pipeline.py` 批量路径没有。
用户按 README 的 `--workers 4` 示例跑批量，首批**每一份文件都失败**。

**修复建议**：`process_single_file()` 入口处 `Path(output_dir).mkdir(parents=True, exist_ok=True)`，
并补「输出目录不存在」的用例。

### P0-3 降级转换标记未进审计链 → 不可逆失真产物被当作正常产物归档

`.doc` → `.docx` 有三级降级链（LibreOffice → textutil → antiword），
`redact_word.py` 内部已正确产出 `degraded_level` / `degraded_note`，且明确注明
「antiword 级**丢失全部格式与表格结构**，调用方必须据此标记并提示人工复核」。

但实测：`grep degraded scripts/redact_all.py scripts/pipeline.py scripts/manifest.py` → **零命中**。

| 断点 | 位置 | 后果 |
|---|---|---|
| `redact_all.py` → manifest | 未透传 | `manifest.json` 无降级标记 |
| `pipeline.py` → 报告 | 未透传 | 批量报告无降级清单 |
| `redact_all.py` → 退出码 | 无 | **降级产物以成功状态返回，CI/调度无从感知** |

**银行影响**：antiword 降级意味着**表格结构整体丢失**——表格里的姓名可能随结构一起消失，
产出物看似脱敏完成、实则内容残缺且无痕。这是典型的「静默失真」，在档案归集环节极难发现。

**修复建议**：降级信息必须进入 manifest（新增 `degraded` 段）、批量报告（独立「降级产物清单」章节），
并在 `degraded_level` 非空时以**非零退出码**或独立状态（如 `degraded`）返回，由调度侧决定是否放行。

### P0-4 无 CI 流水线——文档多处声称「CI 门禁」，实际靠人工本地执行

**实测**：`git ls-files .github` → 仅 2 个 issue 模板，**无任何 workflow**。

而 `CHANGELOG.md` 与 `docs/贡献档案.md` 多处写「CI 门禁」「CI 回归门禁」
（如 `tests/benchmark/test_benchmark_gate.py` 文件头「并作为 **CI 卡口**」）。

实情是：门禁以 **pytest 形态**存在（`test_benchmark_gate.py` 确有 5 项断言），但**无人触发**。
这意味着：

- 本项目积累的**最有价值的资产**（八项指标门禁 + 283 条金标 + 1200 条真实语料零误伤基线）
  保护强度等于「靠人记得跑」
- 任何一次「赶工期合并」，误伤/漏脱回归**不会被自动拦截**
- 贡献档案里「门禁 8 项全 PASS」的历史记录无法复现验证

**修复建议**：新增 `.github/workflows/ci.yml`，最小集为
`lint → unit tests → benchmark gate (八项) → 真实语料零误伤`，
并把 `scripts/bench_metrics.py` 作为唯一阈值源（现状已如此，直接接即可）。
这一项**投入产出比最高**——不改一行规则代码，就把整套质量资产从「纸面」变成「强制」。

## 二、P1 高优先级问题（影响可运维性与可审计性）

### P1-1 缺少密级分级与策略分区——银行场景的核心缺失

当前 14 类敏感项（`REDACTION_LABELS`）**一视同仁**：人名与身份证用同一套替换机制、同等强度。
银行实际要求是**分级分类**：

| 密级 | 典型项 | 处置要求 |
|---|---|---|
| 核心 | 身份证、银行卡号、账号 | 必须不可逆 + 长度校验 + 单独留痕 |
| 重要 | 手机、固话、邮箱 | 不可逆 |
| 敏感 | 详细地址、金额、日期 | 泛化（保留粒度） |
| 内部 | 人名、机构名 | 泛化占位 |

现状缺失：**无密级标签、无策略分区、无「按密级选择脱敏强度」的配置能力**。
`replacement` 配置虽可按标签配占位符，但没有「哪些标签属于哪一密级」这一层抽象。

**改善建议**：在 `config.json` 增设 `sensitivity_levels` 段，按标签映射密级；
`manifest.json` 按密级分组统计；支持「核心密级缺失即阻断」的强校验开关。
同时注意：**泛化程度应可配置**——当前人名一律 `XXX`（3 字符），但 2 字名与 4 字名替换后长度不守恒，
下游若按固定列宽解析会错位（见 P1-3）。

### P1-2 未脱敏中间产物落盘且不清理——合规风险面

`redact_all.py` 在 `tempfile.gettempdir()` 下写入三份**含原文片段**的中间文件：

| 文件 | 内容 | 是否清理 |
|---|---|---|
| `decisions_pending_<pid>.json` | 灰区实体的 `text`（**原始姓名**）、evidence | ❌ 不清理 |
| `redact_override_<pid>.json` | Agent 裁决的实体原文 | ❌ 不清理 |
| `redact_gray_<pid>.json` | 灰区详情 | ❌ 不清理 |

实测：`grep -E "remove|unlink" scripts/redact_all.py` → 零命中。

**银行影响**：脱敏工具的**中间产物**成为新的敏感数据副本，散落在系统临时目录，
无访问控制、无生命周期、无审计。在数据分类分级体系下，这些副本应当与原始文档同级管理。

**改善建议**：
1. 中间文件改写到**受控工作目录**（如 `<输出目录>/.work/`），随任务目录统一清理；
2. 使用 `try/finally` 保证异常路径也清理；
3. 内容改为**仅存指纹与偏移**（如 `sha256(原文)[:12] + span`），裁决文件不含明文；
4. 文件权限显式设为 `0600`。

### P1-3 替换不保证等长／长度守恒，下游结构可能错位

`config.json` 的 `replacement` 中：`ID_CARD` 为 18 字符占位符，而身份证 18 位——**守恒**；
但 `MOBILE` 为 11 字符占位符（守恒）、`PHONE` 为 `0XX-XXXXXXXX`（12 字符，而固话可能 10~12 位——**不守恒**）；
`DATE` 为 `YYYY/MM/DD`（10 字符，对 `2026-11-05` 守恒，对 `20261105` **不守恒**）。

更关键：**人名统一替换为 `XXX`**，则「张三」（2 字）与「欧阳修远」（4 字）替换后长度差 2。
`redact_word.py` 已有等长写回机制（`R-⑳` 等长写回），但姓名走的是 `XXX` 通用替换，
**未按原长度生成占位符**。

**银行影响**：下游若按固定字段宽度解析（导入核心系统的定长字段、按位置截取的文本），
替换后长度变化会导致**后续字段整体错位**，产生比「未脱敏」更难排查的数据污染。

**改善建议**：姓名按原长度生成占位符（2 字名 → `XX`，3 字名 → `XXX`，4 字名 → `XXXX`），
使替换严格等长；日期、固话同理按原长度对齐。此改动需同步核对既有金标断言。

### P1-4 残留审计与保留审计未接入门禁——最后一道防线是手工脚本

`scripts/residual_audit.py`（查脱敏产物中的真名残留）与 `scripts/keep_audit.py`（查误伤/保留项）
是项目的**兜底防线**，但实测：`grep -E "residual_audit|keep_audit" tests/ scripts/bench_metrics.py` → **零命中**。

两个脚本**均无测试引用**，意味着它们本身可能已失效（无人验证），
却又不参与任何自动判定。

**改善建议**：把 residual_audit 的「真名残留 = 0」纳入 `bench_metrics.py` 成为第九项门禁；
keep_audit 转为人工复核清单（它本身带主观判断，不宜全自动化）。
**先验证脚本有效性再接入**——否则会引入一个永远绿的假门禁，比没有门禁更危险。

### P1-5 「无重试幂等」依赖占位符字符串匹配，脆弱且不完整

幂等性当前靠「已替换的占位符（`XXX`/`XX银行`）不会被二次命中」实现（`common_rules.py` 中 5 处幂等守卫）。
问题：

1. **占位符与真实内容的碰撞**：若原文本身含 `XXX`（英文缩写、占位符残留、代码片段），
   系统无法区分「已脱敏的 XXX」与「原文的 XXX」，幂等判断即失效；
2. **占位符格式不统一**：`XX银行`、`XXXX`、`XXX`、`0XX-XXXXXXXX` 并存，
   幂等守卫需逐个模式硬编码（实测确有 5 处分散守卫）；
3. `redact_word.py` 中还出现过「占位符幂等」的注释与实际替换路径不完全一致的情形。

**银行影响**：同一份文档重复脱敏两次，第二次可能对占位符再次加工；
或原文 `XXX` 被误判为已脱敏而**跳过**——后者是漏脱。

**改善建议**：引入统一占位符**注册表 + 哨兵标记**（如不可见 Unicode 私有区标记或结构化占位符对象），
使「已处理」成为**可判定状态**而非字符串猜测；并补「原文含 `XXX`」的专项用例。

## 三、P2 中优先级问题（可维护性）

### P2-1 `_build_patterns()` 单函数 1498 行——规则集的巨石

`scripts/common_rules.py` 5025 行 / 122 个函数，其中 `_build_patterns`（L1840）**独占 1498 行**，
内含 **84 个 `re.compile`** 与大量词表装配逻辑。

这是全项目**最核心也最脆弱**的单元：任何规则改动都要在这 1498 行里定位、插入，
且极易引发「新增规则的层序错误」——#56（D16 二字名层截断三字姓名）正是**层序错误**的产物，
#55 又是一次层序调整。这类事故的根因，就是规则装配被压在一个无结构的巨型函数里。

**改善建议**：拆为「规则注册表 + 声明式层定义」：
```python
RULE_LAYERS = [
    LayerSpec(name="d16_full_3", order=10, pattern_fn=build_d16_full_3, ...),
    LayerSpec(name="d16_full_2", order=20, pattern_fn=build_d16_full_2, ...),
    ...
]
```
层序变成**显式声明的元数据**（而不是代码行的先后），并为「层序」单独立门禁断言
（如「长名层 order 必须小于短名层」）——这正是 #56 类事故的自动化拦截点。

### P2-2 18/28 模块零测试覆盖

实测模块引用扫描结果：

| 状态 | 模块 |
|---|---|
| 有测试引用（9） | `common_rules` `redact_word` `redact_ppt` `redact_all` `name_region_detector` `table_role_detector` `r4_name_scoring` `bench_metrics` `quality_validator` |
| **零测试引用（19）** | `pipeline` `redact_excel` `redact_pdf` `redact_image` `manifest` `entity_detector` `llm_client` `redaction_engine` `prompts` `decision_mining` `keep_audit` `residual_audit` `mine_guard_words` `mine_boundary_pairs` `redact_iterative_v2` `redact_iterative_compare` `redact_llm` `test_common_rules` |

`pipeline.py` 零测试直接导致 P0-1 / P0-2 未被发现；`redact_excel.py`（银行高频格式）
零测试尤其危险。

**改善建议**：按「投产阻断优先级」补测，而非按行数补测：
`pipeline` > `redact_excel` > `redact_pdf` > `manifest` > `entity_detector`。

### P2-3 依赖声明不完整且无版本锁定

实测 `requirements.txt` **未声明** `jieba` 与 `tqdm`，而二者均被实际 import：
- `jieba`：`r4_name_scoring.py:35`、`mine_guard_words.py`（4 处）——R4 评分层的核心依赖
- `tqdm`：`pipeline.py:26`（批量进度条）

同时 13 个依赖**全部无版本约束**，也无 lock 文件。

**银行影响**：生产环境 `pip install -r requirements.txt` 会拉到**当时的最新版**，
可能出现与开发期完全不同的行为（尤其 `jieba` 分词结果随版本变化，直接影响 R4 评分层判据）；
`jieba` 缺失则 R4 层直接不可用，而当前是 `import` 在函数内（`try/except` 吞掉），
**降级静默、无告警**。

**改善建议**：
1. `requirements.txt` 补全 `jieba`、`tqdm`；
2. 提供 `requirements.lock`（`pip freeze` 精确版本）；
3. `jieba` 缺失时**显式告警并禁用 R4 层**，而非静默降级——静默降级在合规场景是反模式。

### P2-4 遗留实验脚本与主链路混放

`redact_iterative_v2.py`（987 行）、`redact_iterative_compare.py`（557 行）、
`mine_guard_words.py`、`mine_boundary_pairs.py`、`decision_mining.py` 与主链路同目录。
实测：前两者**不被任何模块引用**，是 #50 时期的迭代比对工具（含 `except:` 裸捕获 4 处）。

**改善建议**：迁至 `tools/` 或 `research/` 目录并标注「非生产路径」；
裸 `except:` 全部改为具体异常类型。

### P2-5 `full_name_list` 含 32 条污染项

实测 7399 条中有 32 条**不满足「2/3 字全汉字」**格式：

| 类型 | 样例 | 影响 |
|---|---|---|
| 分隔符污染 | `曹超、胡波`、`王素楠/耿攀攀`、`魏晓敏/王素楠` | 永不匹配（白占条目，且说明采集链有缺陷） |
| 拼音残留 | `李丹JGNL`、`刘浩CL`、`王蕾DZYH`、`张琳SSNL`（10 条） | 同上；推测源自某业务系统的姓名+工号字段 |
| 复姓超长 | `端木凡豪`、`皇甫鑫鑫`、`欧阳一帅` 等（22 条） | **4 字复姓**，2 字名层虽已修复（#56），但 3 字层边界语义仍需逐条核对 |

**银行影响**：D16 是「本项目语料内出现过的姓名」，其**数据血统不干净**——
拼音残留条目说明采集源混入了含工号的字段。此类污染虽当前不致误伤（不匹配即不生效），
但会让「D16 有 7398 个真名」这一审计陈述失真。

**改善建议**：清洗词表并留痕清洗日志（哪 32 条、为何剔除）；
**更重要的是补充数据来源说明**——D16 的来源、采集方式、覆盖范围当前在仓库中无处可查，
这是审计场景的硬伤（见 P2-6）。

### P2-6 D16 词表数据血统不可追溯

`full_name_list`（7398 条有效）的**来源在仓库中无任何说明**：
`docs/` 54 个文档中无一记录其采集来源、采集时间、覆盖人群范围、清洗规则。
唯一的间接线索是 CHANGELOG 中「来源：姓名清单」六字。

**银行影响**：脱敏规则依赖一份**来源不明**的黑名单。若该清单本身含非自然人条目
（见 P2-5 的拼音残留），无法判断污染范围，也无法向监管说明「本系统依据何种依据识别个人身份信息」。

**改善建议**：为所有词表（`full_name_list` / `common_name_dict` / `common_word_guards` / `biz_guard_words`）
补 `docs/词表数据来源说明.md`，逐表记录：来源、许可、采集时间、覆盖范围、清洗规则、已知边界。
`common_name_dict` 已有（Apache-2.0 + 许可全文入库），**其余三张表均缺**。

## 六、投产前必须回答的三个合规问题

架构之外，有三件事需要业务与合规共同拍板，架构师无法代答：

1. **「XXX」是否满足银行对个人身份信息的不可逆要求？**
   当前人名一律替换为 `XXX`。若监管或内控口径要求「不可复原且不可与其他数据关联识别」，
   需评估 `XXX` 是否够格；若要求更强，可考虑「哈希 + 盐」或「按文档 ID 派生」的确定性假名，
   后者可在保持不可逆的同时支持同文档内一致性。

2. **脱敏产物的保存期限、访问控制与销毁流程由谁定义？**
   工具只管生成，不管留存。银行的 `manifest.json` 需要配套的密级标签、
   留存期限与销毁台账，否则审计留痕本身变成新的合规负担。

3. **D16 词表的来源与合规依据如何向监管说明？**
   这是全套规则的地基。当前**无任何来源说明**（P2-6），且含 32 条污染项（P2-5）。
   若被问及「你凭什么认为这个字符串是人名」，当前答不上来。
