## 一、问题定性

Issue #45 将 `surname_pool` 201→415 字、`name_pool` 152→1285 字后，**规则A 字符池粗筛**的可匹配模式空间从 ≈3 万扩至 ≈53 万（**18×**）。超出真实人名增量的部分全部是日常汉语常用字，与业务词汇高度重合，导致大面积无效替换。

> 口径说明：扩池前基线为 `main@5479569`（Issue #45 之前的最后提交），姓氏池 **201 字**、名字池 152 字。社区草案正文曾记为「196 字」，本文档以仓库实际值为准。

**关键归因**：误伤几乎全部来自规则A，**D16 精确匹配层本身是 #45 的正确设计**（104 条语料仅 1 条误伤，且"高明"属人名/词义双解、人名场景正确）。因此 #45 的数据资产与 D16 规则**不需回滚**，需改造的是规则A。

## 三、根因

### 3.1 三层检测的职责边界在扩池后失衡

| 层 | 规则 | 匹配依据 | 扩池后表现 |
|---|---|---|---|
| 精确层 | D16 `full_name_list` | 7398 已知全名（枚举） | 误伤 **1.0%**，召回可靠 |
| 粗筛层 | 规则A `姓 + [name_pool]{1,3}` | 415×1285 笛卡尔积 | 误伤 **54.8%** ⬅️ 问题主体 |
| 兜底层 | R4 评分层（jieba + 6 特征） | 上下文语义 | 未启用（`name_mode` 默认 enum） |

### 3.2 高危单姓与常用词首字正面碰撞

415 姓中大量本身即常用词首字：`成 方 平 常 和 田 米 干 车 费 贝 何 余 刁 卜 危 安 宁 尚 甘 习 靳 莫 孔 老 庄 荀 孟 单 关 解 应 宗 丁 宣 邓 洪 包 诸 左 石 崔 吉 钮 龚 林 门 龙 段 郑 牛 浦 施 零 厉 刘 …`

这些姓氏 + 常见字几乎必然组成真实存在的词：`成本/成立/成功/成员`、`渠道`、`流程`、`日常/业务`、`单元/元宇宙`、`温州/宁波/江苏`。

### 3.3 无右边界约束放大了破坏范围

规则A 自 Issue #5 起为防漏脱敏已移除 `(?![a-zA-Z0-9])`，贪婪量词 `{1,3}` 会一路吃到后续汉字，"渠道拓展"整个 4 字被替换。

### 3.4 分隔符入池导致名单整段吞并（社区新增定位）

「成员：李思远、周慧敏、王根利负责需求」被整段吞掉的根因：

- 规则A 实际命中 `['李思远、', '周慧敏、', '王根利']` —— **`、`（顿号）本身在扩池后的 `name_pool` 中**；
- 姓名字符组贪婪匹配因此跨过顿号，把「李思远、」整块当作 4 字人名；
- 扩池前 base 档的 `name_pool` **不含 `、`**，该现象不出现 → 印证"扩池引入"归因；
- 对应措施 **M9：`name_pool` 移除标点类字符**（顿号、斜杠），比局部 `_apply_list_continuation_pass` 补丁更根治。
- ⚠️ 注意：`name_pool` 中还有 15 个大写字母（`X L J S H C T N Z G E B D K`）属脱敏占位符字符集，**必须保留**；
  字母类污染改由规则层「姓名形态判定须全为汉字」约束处理（详见 Issue #50）。

## 四、整改方案：三层置信分级（方案 R）

### 4.1 设计原则

**误伤与漏脱不对称** —— 漏脱属合规红线，误伤属可用性缺陷。分级策略以"高置信直接脱敏 / 中置信需上下文佐证"分层，**不做无差别收紧**。

### 4.2 规则集

| 层 | 规则 | 触发条件 | 置信 | 动作 |
|---|---|---|---|---|
| **R1** | D16 精确表 | 命中 `full_name_list` | 高 | 直接脱敏 |
| **R2** | 低危姓 + 2~3 名字字 | 姓氏 ∉ `high_risk_surnames` | 中 | 直接脱敏 |
| **R3** | 高危姓 + 3 名字字 | 姓氏 ∈ `high_risk_surnames`，需三字全名 | 中 | 直接脱敏 |
| **R4** | 上下文锚点 + 任意姓 + 1~2 名字字 | 角色词/名单邻域 | 中 | 脱敏 |

**上下文锚点词表**（复用 #38 D8/D11 角色槽位）：
`负责人 / 联系人 / 成员 / 人员 / 组长 / 经理 / 主任 / 总监 / 名单 / 参会 / 出席 / 签名 / 签字 / 汇报 / 由 / 请 / 联系 / 支持人员 / 配合人 / 经办人 / 办理人 / 授权人 / 审批人 / 复核人 / 申请人 / 填报人 / 签字栏`

### 4.3 参数网格搜索结果

以"误伤最少 + 真名召回最多"为目标，对 `(低危姓 min~max, 高危姓 min~max, 是否启用锚点)` 做全网格搜索（2×3×2×2×2 = 48 组）：

| 排名 | 配置 | 误伤 | 真名 | 漏脱真名 |
|---|---|---|---|---|
| 1 | 低危 2~1 / 高危 3~3 / 锚点 | 4 | 7 | 王小红、张明、樊霖、司马光、李雷 |
| 2 | **低危 2~2 / 高危 3~3** | **9** | **9** | 张明、樊霖、李雷 |
| 3 | 低危 2~3 / 高危 3~3 | 9 | 9 | 张明、樊霖、李雷 |
| 4 | 低危 2~1 / 高危 2~2 | 14 | 9 | 张明、樊霖、李雷 |

**选定配置：低危姓 `{2,3}` + 高危姓 `{3,3}` + 上下文锚点**。理由：

- 排名 1 的"低危 2~1"是空区间（等价于关闭低危规则），虽误伤最低但漏脱 5 个真名，**违反"漏脱优先于误伤"的红线**
- 排名 2/3 在误伤 8.7% 前提下把真名召回从 7 提到 9，漏脱仅剩 3 个**二字名**
- 漏脱的 3 个（张明/樊霖/李雷）在真实场景几乎总伴随角色词上下文，由 R4 锚点覆盖：

| 场景 | 结果 |
|---|---|
| 负责人：张明 | ✅ 脱敏 |
| 参会人员李雷 | ✅ 脱敏 |
| 请樊霖办理 | ✅ 脱敏 |
| 由李雷签字 | ✅ 脱敏 |
| 总行支持人员：张明 | ✅ 脱敏 |
| 组长是樊霖 | ❌ 漏脱（"是"字未列入锚点连接符）|

### 4.4 残余误伤与归属

分级后残余 9 条误伤，全部属**词义消歧**范畴，不应在正则层硬编码：

| 残余误伤 | 性质 |
|---|---|
| 渠道拓展、单元测试、元宇宙、客户经理 | 通用词，需 R4 语义评分 |
| 宁波银行、甘泉资本、江苏卫视 | 机构名，需银行/机构名规则先行 |
| 高明、叶子涵 | 人名/词义双解，人名场景正确 |

**处置建议**：优先把机构名规则（银行名/城市名）调整到姓名规则**之前**执行，可消解"宁波银行/甘泉资本"2 条；其余交 R4 评分层（#17）仲裁。

### 二、M9 实施记录（2026-10-25）

**实施方式：数据修复 + 载入期结构性防护（双层）**

| 层 | 内容 | 说明 |
|---|---|---|
| **数据修复** | `scripts/config.json` 的 `name_pool` 移除 `、` `/` | 1285 → **1283** 字；改动仅 2 字符，`surname_pool` / `full_name_list` 零改动 |
| **结构性防护** | `scripts/common_rules.py` 新增 `_clean_name_pool()` / `_is_name_pool_pollution()` / `get_name_pool_chars()`，在**载入期**统一清洗 | 规则层（`common_rules` 3 处 + `r4_name_scoring` 1 处 + `redact_iterative_compare` 1 处）全部改用清洗后的池 |

**为什么不能只改 config.json**：字池是人工维护的，后续任何一次扩池都可能再次混入标点。只改数据等于把"下次再犯"的成本留给未来的维护者；在载入期做一次拦截，M9 才是根治而非一次性修补。

**清洗规则**：剔除**标点/符号类**字符（Unicode `P*`/`S*` 类别 + ASCII 非字母数字 + 正则元字符 `[]^-`），**保留汉字与占位符大写字母**（`_PLACEHOLDER_LETTERS`）。小写字母一并剔除（占位符集只用大写，小写无占位符用途却会扩大匹配面）。字母污染的危害（`「张三ABC」` 被判为姓名）由规则层的「姓名形态判定须全为汉字」约束另行处理，**不在 M9 范围内**。

### 三、M9 附带修复：空 `name_pool` 触发 `IndexError`（既有缺陷，非 M9 引入）

**现象**：当 `config.json` 的 `name_pool` 缺失或为空时，规则A 的名字字符类退化为 `[]`。Python `re` 把 `]` 当作字符类的**首字符**（字面量），字符类因此一路向右吞到下一个 `]`，把 `){1,3})(和|与|及|或者|以及)(丁|万|...|[` 全部吞进字符集内，导致连词正则的 **3 个分组塌成 1 个**；`_conj_repl` 调用 `m.group(2)` 抛 `IndexError: no such group`。

**根因**（`git stash` 对比确认**修复前同样报错**，属既有缺陷）：

```python
np_chars = _clean_name_pool(cfg.get("name_pool", "伟强志建华文静宇轩浩然俊杰明辉晨曦"))
name_class = "[" + np_chars + "]"        # ← np_chars 为空时即 "[]"
```

注意 `cfg.get(key, default)` 的 default **只在 key 缺失时生效**；`name_pool` 存在但值为 `""` 时拿到的是空串而非 default。

**修复**（随 M9 一并落地，因二者同处一条载入期链路）：

| 动作 | 位置 | 说明 |
|---|---|---|
| 提取内置兜底池 `_FALLBACK_NAME_POOL` | `common_rules.py` | 原先只内联在规则A 一处，现提升为模块级常量，供全部构造点共用 |
| 新增 `_get_name_pool_chars(cfg)` | `common_rules.py` | 统一入口：清洗 → 为空则回退兜底池；带缓存（XX 恢复段每次 `apply_redactions` 都会取用，缓存后运行期零开销） |
| 新增 `_build_name_char_class(chars)` | `common_rules.py` | 统一构造字符类：**转义** `]` `^` `-` `\` `[` 等元字符，杜绝污染字符撑开字符类 |
| 收敛全部消费点 | `common_rules.py` ×3、`r4_name_scoring.py` ×1、`redact_iterative_compare.py` ×1 | 5 处统一走 `_get_name_pool_chars` / `_build_name_char_class` |

**修复效果**：

| 验证项 | 修复前 | 修复后 |
|---|---|---|
| 空池时连词正则分组数 | 1（塌陷） | **3**（正确） |
| 空池时 `apply_redactions` | `IndexError: no such group` | **正常返回** |
| 正常池下正则行为 | — | 与修复前**逐字节一致**（字符类构造结果相同） |
| 66 份真实文档输出 | — | 与修复前**完全一致**（逐字符比对通过） |

> **边界说明**：本项属**既有缺陷**，非 M9 引入。用户授权范围为「处理 #49 M9」，因该缺陷与 M9 同处「name_pool → 字符类」这条载入期链路、且修复面仅 3 个函数、无行为副作用（正常配置下输出逐字节相同），故一并修复并在此显式标注，便于社区复核。

### 四、P1 实施记录：场景分层姓名规则（2026-10-26）

> 本节记录 P1 分级改造的**实证结论与最终方案**。所有数字均来自 119 份真实文档 + 102 条通用语料 + 12 条真名样本的实测，可复现（评估器见 `.workbuddy/tmp/p1_eval_new.py`）。

#### 4.1 核心结论：字频单维度存在结构性天花板

先前的分级思路默认「收紧规则A 即可同时降误伤、保召回」。实测否定了这一前提：

| 闸门档位 | 金标召回 | 库外召回 | 通用语料误伤 | 难例误伤 |
|---|---|---|---|---|
| `surname≥5` + `尾字≥12` | 318/453（70%） | 122/178 | **12** | 675 |
| `surname≥0` + `尾字≥12` | 335/453（74%） | 124/178 | 20 | 888 |
| `surname≥0` + `尾字≥3` | 428/453（94%） | 163/178 | 30 | **1817** |

**不存在**同时满足「零漏脱」与「低误伤」的参数点——放宽到覆盖 94% 必然带来 1817 条难例误伤。

原因：上下文信号与字频**弱相关**。实测「锚点覆盖 45 个金标名、名单块覆盖 336 个」，这些被上下文救回的真名在字频维度上与业务词完全不可分。

**这直接推导出方案方向：不能一刀切收窄，必须按场景分层**——不同场景的证据来源不同，就该用不同的判据。

#### 4.2 最终方案：四层场景分层

| 层 | 场景 | 证据来源 | 匹配范围 | 依据 |
|---|---|---|---|---|
| **S1** | 裸姓名（无任何上下文） | 字频 | 严闸门：姓氏位 + 尾字热/前字温 | 字频在此是唯一证据，故必须最严；这是误伤的主要来源地 |
| **S2** | 名单块（顿号/逗号并列） | 列表一致性 | 块内全池 | 名单块信号覆盖 336 个金标真名，误伤仅 19 条（对比字频宽松档 1817） |
| **S3** | 强上下文（角色锚点/冒号/介词） | 上下文 | 全池 | 上下文本身即证据，再叠字频闸门属「连坐」，会误伤真实姓名 |
| **S4** | 名单块但块内无 D16 确认真名 | 纯结构一致性 | 块内全池 | 库外真名所在块的「同块 D16 邻居」命中率 **0%**，S2 对此完全无效，需独立取证 |

#### 4.4 最终量化结果

> **口径说明**：下表「M9 基线」列为**完整生产链路**（`apply_redactions`，含 pre/规则链/后处理）的实测值，而非仅规则链。此前记录的「M9 误伤 10/102」是规则链口径，完整链路下 M9 实为 **52/102** —— M9 的无差别全池匹配既零漏脱，也误伤过半通用语料。

| 指标 | M9 基线 | P1 终版 | 说明 |
|---|---|---|---|
| 通用语料误伤 | 52/102 | **9/102** | 修复 43 条，**零新增**；9% < 10% 目标达成 |
| 12 条真名召回 | 7/12 | 5/12 | 漏 7 条（张伟/艾成军/邹阳/陈黎/汪晶晶/樊霖/韩梅梅） |
| 824 条金标保留率 | 824/824 = 100% | **791/824 = 96.0%** | 33 条漏脱（合规红线项，见 4.5） |
| 库外真名保留率 | 231/231 = 100% | **208/231 = 90.0%** | 23 条漏脱 |

**取舍说明**：M9 基线以「零漏脱」为代价换取 52 条通用语料误伤。P1 把误伤压到 9 条（-43 条），代价是 33 条金标漏脱。这是「误伤属可用性缺陷、漏脱属合规红线」取舍下的显式交换——**零漏脱与低误伤不可兼得**（见 4.1 字频天花板），P1 选择先把可用性缺陷压到目标线内，并把剩余漏脱逐条定位到具体成因（4.5）供后续用新证据维度攻关。

**阈值网格搜索结论**（45 组，sur∈{0,1,2,3,5} × hot∈{8,12,16} × warm∈{2,3,5}）：

| 参数组 | 误伤 | 金标 | 库外 | 难例误伤 |
|---|---|---|---|---|

| sur=1 / hot=8 / warm=2 | 15/102 | 94.7% | 85.7% | 468 |
| sur=2 / hot=8 / warm=2 | 11/102 | 94.1% | 83.5% | 571 |

#### 4.7 实施中发现并修复的五个实证缺陷

**（1）量词语义错误 —— 名字位长度约束失效**

旧写法 `[温]{0,2}[热]` 再套 `{1,3}`，实际等价于 `[温]{0,2}[热]{1,3}`：**量词落在尾字类上而非名字位上**，名字位可长达 5 字、尾字判定失效。改为按长度显式展开（`_build_name_pos_class`）：

```
名字位 1~3 字 → [温]{0,2}[热]
名字位 2~3 字 → [温]{1,2}[热]
```

**（2）S2 与 D16 的执行顺序 —— 救援信号自我销毁**

S2 的证据是「块内含 D16 已确认真名」。若 S2 排在 D16 之后，D16 先跑把确认真名替换成 XXX → 证据消失 → 名单块整块漏脱。

修复顺序后发现第二个缺陷：S2 只替换非 D16 项、保留 D16 项，而占位符 `XXX` 是 **ASCII 字母**，紧贴保留的 D16 名后（`郑云XXX`），使 D16 层右边界 `(?![a-zA-Z0-9])` 失效——该 D16 名永远匹配不到。**实测金标保留率从 88.7% 掉到 63.7%**。

最终解法：**块内各项统一替换**，不再把 D16 项留给精确层。列表一致性证据已判定「整块都是人名」，整块脱敏既正确，又让 S2 与 D16 的执行顺序彻底解耦（谁先谁后都对）。

**（3）块正则用前瞻 —— 整块未被捕获，块内一致性证据整体失效**

S2/S4 的块正则原写作 `(?:{sep}(?={item}))+`——用**前瞻**表达「分隔符 + 项」。但前瞻不消耗文本，捕获组 `block` 实际只含「**第一项 + 分隔符**」，整个块并未被捕获。

后果是两条规则赖以成立的证据同时失效：
- S2「块内含 D16 确认真名」退化为「**该单项**是否在 D16」
- S4「块内每一项都符合严格形态」退化为「**该单项**符合即可」

实测症状：真实文档 `王松/吴学亮/叶新林/马娟` 中，块只捕获到 `叶新林/`，反而是 D16 确认真名的叶新林漏脱。修正为真正捕获整块后，金标保留率 95.0% → **96.2%**，库外 85.7% → **90.0%**，误伤零新增。

**（4）D16 右边界排除数字 —— 「名字+数字」整类漏脱**

原右边界 `(?![a-zA-Z0-9])` 把「强峰4.3业务准备」这类形态整类拦掉，119 份文档中导致 **60/824 条金标漏脱**。数字并非英文，应允许跟随；字母仍需排除（库内 15 条带字母后缀的条目如 `刘磊CL`/`李丹JYEB` 已按长名优先整体匹配）。

**（5）D16 左边界排除 ASCII/数字 —— 「代号+姓名」整类漏脱**

原左边界 `(?<![a-zA-Z0-9])` 把「ASCII/数字 + 姓名」形态整类拦掉，而真实文档里这类形态极常见（表格里姓名紧贴系统代号/人数）：`IDATA-BDS季海涛` / `FB-APPSVR卫海啸` / `研发组11张海翔` / `OF-BANK赵乐品`。实测导致多条**库内确认真名**漏脱。

但**不能无差别放宽**：改成「不排除 ASCII/数字」会让「组余翔」「宋广举」这类紧跟汉字的库内名漏脱（实测多漏 8 个）。最终按**名字长度分层**：2 字名保持严格（防「白天鹅」误伤），3 字及以上放宽。

**附带修复**：D16 库中混入字段标签「姓名」，导致「请填写姓名」→「请填写XXX」。以显式清单 `_D16_NON_NAME_ENTRIES` 过滤（而非改数据文件，上游修正后可自动恢复）。

#### 4.8 P2 业务词保护守卫（2026-10-26）

> 本节记录 #49 剩余 **17 处业务词误伤**的收敛过程与实测结论。

#### 4.8.1 残余误伤的精确归因

P1 落地后，通用语料误伤降至 9/102，但真实文档里仍有 17 处业务词被误脱。逐条复现并归因，成因分**四类**（各走独立通道，不能用单一补丁覆盖）：

| 类型 | 代表片段 | 命中通道 | 根因 |
|---|---|---|---|
| **A. 跨词边界切词** | 金子、付金、余本金、池业 | 规则 A 粗筛层 | 业务词被从中间切开，「金」「付」「单」「余」「池」恰好在姓氏池或名字池内 |
| **B. 介词后全池** | 上述所有、全部、以上、如下 | 规则 E（介词后全池匹配） | 「上述/所有/以下/相关」等指示词本身不在任何闸门内，被当成人名 |
| **C. 名单块纯形态误判** | 白名单、单位、活期、定期、票据池、商票保贴 | S2/S4 名单块、D16 顿号名单保形通道 | 这些词恰好符合「姓氏 + 名字池字」的严格形态，被当成人员名单 |
| **D. 银行渠道名** | 电子银行、电子银行部 | PRE#23 银行名兜底 | `_BANK_BIZ_SYSTEM_RE` 缺「电子」，渠道名未被识别为泛称 |

> 关键洞察：**四类成因分属四条互不相干的代码通道**。只在规则 A 加守卫最多解决 A 类；B/C/D 类必须各自在对应通道处理，否则改动会互相干扰。

#### 4.8.2 方案：业务词保护表 + 三类守卫（G1/G2/G3）

**业务词保护表**（`config.json` → `biz_guard_words`，135 词）：

| 构建方法 | 说明 |
|---|---|
| 语料挖掘 | 从 119 份真实文档（`<w:t>` 抽取正文）+ 102 条通用语料，挖 2~4 字高频 CJK n-gram，得 9442 条候选 |
| 去碎片 | 被更长候选词包含者丢弃 |
| 人工补充 | 70+ 银行业务词（保证金、白名单、票据池、商票保贴…）+ 频次 ≥150 的 3 字词 |
| **双向真名过滤** | 与 D16 全名库（7398 条）、824 条金标真名**双向**剔除有包含关系的词 |

> **双向过滤是守卫的安全前提**：词表内不可能含任何真名，故业务词守卫**在结构上不可能造成真名漏脱**。回归测试 `test_biz_guard_table_has_no_real_names` 锁定这一不变式。

**三类守卫**（`common_rules.py`）：

| 守卫 | 判定 | 解决的问题 |
|---|---|---|
| **G1 跨界守卫** | 命中片段与某业务词区间**相交**（词的尾字落在命中内 / 命中首字落在词内 / 命中被词完全包含） | A 类：切词切到了业务词上 |
| **G2 整体命中守卫** | 命中片段**本身就是**业务词 | C 类：「活期」「定期」整词命中 |
| **G3 指示词守卫** | 命中片段含指示词/代词（上述/以下/如下/相关/其他/所有/全部/各个/各项/各类）且不构成姓名前缀形态 | B 类：介词后全池 |

**G3 的豁免条件**：`matched[0] in SURNAME_SET and len(matched) <= 3` 时不判为指示词——避免以姓氏字开头的真名（如「肖相关」）被误放过。

**挂载点**：

| 通道 | 挂载方式 |
|---|---|
| `_name_guard_sub_counted`（规则 A 主入口） | `_is_protected_by_common_word` 判定之后追加业务词守卫 |
| `_name_guard_sub`（非计数版） | 同上 |
| S2 `_list_rescue_repl` | 块内**任一项**命中业务词 → **整块放弃**（名单一致性证据失效） |
| S4 `_s4_rescue_repl` | 同上（S4 证据是「块内每项都是严格姓名形态」） |
| `_list_name_repl`（D16 顿号名单保形） | 列表项命中业务词 → **保留该项** |
| `_BANK_BIZ_SYSTEM_RE` | 补入「电子」→ D 类渠道名识别为泛称 |

> **为什么名单块要「整块放弃」而非「只跳过该项」**：S2 的证据是「块内含 D16 已确认真名」，S4 的证据是「块内每一项都符合严格姓名形态」。一旦块内出现业务词，说明**整个块是业务枚举而非人员名单**——只跳过一项仍会把「白名单」当人名单脱敏。整块放弃是证据层面的一致处理。

#### 4.8.3 性能：窗口扫描

首版实现对每处命中都全量遍历 135 个业务词做 `str.find`，119 份文档评测从 55s 涨到 **超时被杀**。改为：

1. **首字倒排索引**（`_get_biz_words_by_first`）：单次扫描 O(len(seg) × 该首字下的词数)；
2. **局部窗口**：跨界只可能发生在命中边界附近，业务词最长 4 字，故左右各取 6 字足以覆盖判定，避免全文本扫描。

改后耗时回到 **55.7s**，与基线持平。

### 4.9 修复 #45 扩池引入的地址占位符回归（2026-10-26）

#### 4.9.1 问题发现与定性

在全量回归中，`tests/test_r15_zhaohui.py::test_address_tail` 断言失败：

```
assert "XX路XX号" in out
AssertionError: 地址占位符不对：'XXXXX号'
```

该用例属 **Issue #45 扩池引入的既有回归**，与本 Issue #49 的整改无直接因果关系，但在 #49 P2 落地后做全量门禁复核时暴露。

**根因**（`git bisect` 跨提交二分定位，引入点 `86f0bd5` / Issue #45）：

1. #45「精确全名匹配」把 `name_pool` 从 152 字扩到 1283 字；
2. 「路 / 道 / 号 / 园 / 京」等**地址用字**随之进入名字池；
3. `scripts/common_rules.py` 的「恢复被地址通道误截断的姓名」后处理段，其语义是「地址通道把一个**姓名**截断了 → 还原成完整姓名」。当它扫描到地址通道**自己输出的**占位符 `XX路` / `XX号` 时，因「路 / 号」已在名字池中、且前一个字「于」等在姓氏池中，于是把**地址占位符**误判为「被截断的姓名片段」并合并成 `XXX`：

   ```
   位于XX路XX号  →  XXXXX号        # 地址占位符被吃掉、路名与门牌号的结构丢失
   ```

**影响面**：地址回溯式脱敏通道（`_apply_address_pass`）的**终态**结构被破坏 —— 门牌号、路名的可读占位符消失；下游若依赖「XX路XX号」结构做二次校验或人工复核，将失去结构信息。

#### 4.9.2 修复方案：路型/门牌后缀守卫

在恢复段的合并判据中新增一条守卫（`scripts/common_rules.py`）：

```python
# 路型/门牌后缀守卫（2026-10-26，修复 #45 扩池引入的既有回归）
_RECOVERY_ROAD_SUFFIX_CHARS = frozenset("街路巷弄道号")
...
if _ch_after in _name_chars:
    # 路型/门牌后缀守卫：XX 是地址通道自身的占位符，非姓名片段
    if _ch_after in _RECOVERY_ROAD_SUFFIX_CHARS:
        _pos = _idx + 2
        continue
```

**判别依据**：地址通道的终态就是「XX路XX号」。若 `XX` 之后紧跟的字属于**路型/门牌型后缀**（街/路/巷/弄/道/号），说明这个 `XX` 是地址通道自己吐出的占位符，**不是**被截断的姓名片段 —— 此时绝不合并。

**与 R-⑱ 机构后缀守卫的关系**：

| 守卫 | 拦的形态 | 语义 |
|---|---|---|
| R-⑱ 机构后缀守卫 | `XX银行` / `XX支行` / `XX公司` | 机构占位符，非截断姓名 |
| **路型/门牌后缀守卫（本次新增）** | `XX路` / `XX号` | 地址通道自身的占位符，非截断姓名 |

**行政后缀（镇/村/县/区/市/省）刻意不纳入**本守卫 —— 「XX镇」是**中间态**而非终态，必须仍由本段合并回完整姓名，以保住「黄日镇 → XXX」这一既有修复场景。
