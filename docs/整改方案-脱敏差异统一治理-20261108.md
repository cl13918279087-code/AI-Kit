## 一、为什么需要合并整改

比对报告与 5 条 issue 描述的是**同一批缺陷的不同切片**。若按 issue 各自并行实施，会出现三处结构性冲突：

| 冲突点 | 涉及 issue | 冲突性质 |
|---|---|---|
| **同根因、两条通道** | #58（名单通道 `_apply_plain_list_pass`）、#59（锚点扩散通道 `_apply_anchor_expand_pass`） | 根因同为「缺人名证据判据」，若分别实现两套门控，将出现双重判定、行为不可预测 |
| **层与层重叠** | #57（规则C 长度量词）、#60（字池覆盖 + 频次闸门） | #57 修的是**匹配长度**，#60 修的是**字形覆盖**；#60 的验收明确依赖 #57 先落地（issue 原文已声明） |
| **组织名归属交叉** | #59（槽位内职务标签）、#61（机构名通名+后缀） | 「计财部」既可能被槽位通道处理、也可能被机构通道处理，缺少统一归属会重复脱敏或互相豁免 |

**结论**：改为「**一次证据层改造 + 三批场景接线**」，5 条 issue 降级为该方案下的 5 个子任务。

## 二、实测复核：issue 描述与实现的偏差

整改前对 5 条 issue 的每条根因做了代码级复核，**发现 3 处偏差**，直接影响方案设计：

### 偏差 1：#61 根因 2 不成立（保护表**已接线**，问题在语义参数）

issue #61 原文：

> 实测 `cr._is_protected_by_common_word_guard('科技部', 0, 4)` 返回 `True`，
> 但**组织名通道根本没有调用该守卫**——保护表只接入了姓名通道。

实测复核（`scripts/common_rules.py:2825`）：

```python
def _org_name_repl(m):
    if _is_protected_by_common_word_guard(m.string, m.start(), m.end(),
                                          strict_longer=True):   # ← 已调用
        return m.group(0)
    return rep.get("ORG", "XXXX")
```

**组织名通道确实调用了守卫**，但传的是 `strict_longer=True`。该参数的语义是「只有表内词**严格长于**命中片段才算豁免」——即「科技部」片段与表内词「科技部」**等长**，故不豁免。

| 调用形式 | `科技部` 结果 | 语义 |
|---|---|---|
| `_is_protected_by_common_word_guard('科技部',0,4)` | `True` | 等长即豁免（issue 打印的是这个） |
| `_is_protected_by_common_word_guard('科技部',0,4,strict_longer=True)` | `False` | 等长不豁免（**通道实际用的**） |

**真实根因**是「G4-S 前缀成词整体保留」策略与「通用词保护表」两条规则的**语义优先级未定义**，而非接线遗漏。修复点因此从「补接线」改为「定义优先级 + 拆表」（见 §4 批次二 D-2）。

> 连带说明：`strict_longer=True` 是 Issue #53 §3.2 的有意设计（否则「科技部」这类独立组织词永不被脱敏）。因此**不能简单改为 `False`**——那会使「信息科技部」这类前缀成词场景同时失去保护。正确做法是把「独立通用词」与「前缀成词」拆成两张表。

### 偏差 2：#57 方案 A 的回退逻辑不完整

issue #57 方案 A：「贪婪匹配 + 尾部职务字回退」，规则描述为「匹配片段末字若为职务后缀字，则回退 1 字」。

原型实测（`scripts/verify_remediation_design.py` 第 2 节）：

| 输入 | issue 方案 A 预期 | 实测（回退 1 字） | 正确结果 |
|---|---|---|---|
| `负责人：蔡昀煜` | `XXX` | `XXX` ✅ | `XXX` |
| `组长：樊霖副组长` | `XXX副组长` | `XXX副组` ❌ | `XXX副组长` |

**回退 1 字不足以剥离「副组长」这类双字职务词**。正确解法是「回退到**职务词起点**」——即贪婪匹配后识别尾部长度 ≥2 的职务词整体剥离。原型验证：

```
负责人：蔡昀煜      → 负责人：XXX
组长：阮秋鸣        → 组长：XXX
成员：吴文静        → 成员：XXX
组长：黄宽钊        → 组长：XXX
组长：樊霖副组长    → 组长：XXX副组长      ← 职务词整体保留
副组长：各条线副行长、总监 → 副组长：各条线副行长、总监   ← 整段不动
领导：总经理        → 领导：总经理
```

## 三、核心设计：证据分层模型

当前实现的判定逻辑是**枚举式豁免**——「形态像敏感实体 → 逐块找豁免理由 → 找不到就脱」。这是中文场景下的结构性缺陷：并列短语的组合无穷，穷举保护表必然漏（这正是 #58 观察到的现象）。

改为**证据分层**，按四层组织，每层的判据、优先级与失败兜底均显式定义：

| 层 | 名称 | 判据 | 缺省动作 |
|---|---|---|---|
| **L1** | 姓名证据层 | D16 全名 / 通用人名词典 / 姓氏+名用字(+字频闸门) / 上下文锚点 | 无证据 → **不脱** |
| **L2** | 职务标签层 | `prefix_forms + suffixes` 组合式声明（#59 方案） | 命中 → **整体保留** |
| **L3** | 机构实体层 | `org_stems + org_suffixes` 组合式 + 简称映射（#61 方案 A/C） | 命中 → **整段脱敏** |
| **L4** | 通用词护栏层 | 业务词表 / 保密标识短语 / 通用并列短语 / 边界对 | 命中 → **整体保留** |

### L1 的关键修正：证据判据必须叠加字频闸门

issue #58 的证据判据第 3 条为「该块首字 ∈ 实证姓氏集，且其余字 ∈ 名字用字池」。**实测该判据单独使用会引入误判**：

| 词 | 首字是姓？ | 余字在名用字池？ | 朴素判据 | 叠加字频闸门 |
|---|---|---|---|---|
| `方案设计` | ✅（方） | ✅ | **误判为姓名** | 正确排除 |
| `金融同业` | ✅（金） | ✅ | **误判为姓名** | 正确排除 |
| `日常运营` | ❌ | ✅ | 正确排除 | 正确排除 |
| `内部资料` | ❌ | 部分 | 正确排除 | 正确排除 |

原型实测（`scripts/verify_remediation_design.py` 第 1 节，40 个样本）：

```
正向样本（真名，应判 True）：16 例 → 命中 12 例
  未命中 4 例：李熔、王谧、成葭、刘兆缋  ← 均为字池缺字，属 #60 范畴
负向样本（职务标签/通用词，应判 False）：24 例 → 误判 0 例
```

**结论**：L1 判据必须写成「姓氏 ∈ surname_pool **且** 余字 ∈ name_pool **且** 尾字字频 ∈ hot∪warm **且** 非业务词/护栏词」，四者缺一不可。这与 #60 方案 1 的「GB2312 全量入池需与保护表双向互斥」是同一风险的两种解法——**叠加闸门的方案风险显著更低**，应作为首选。

### L1/L2/L3 的缺省方向不对称（设计取舍）

| 场景 | 判定方向 | 理由 |
|---|---|---|
| **结构化槽位**（角色锚点后、名单块内） | **默认保留，需正向证据才脱**（strict） | 一处漏脱 = 可追溯的单点事件，走人工复核；一处误伤 = 大面积不可预期的可用性事故（如 64 页 PPT 页脚全被抹）。两者不同量级，缺省应倒向可追溯一侧 |
| **非结构化正文** | **默认宽松，配合上下文锚点召回**（loose） | 正文叙述型人名（"XX行长指示…"）不在名单区、无槽位，严格模式会造成系统性漏脱 |

> #58 §六 已提出 `list_evidence_gate.mode: strict/loose` 的双档设计，方向正确。本方案将其从「名单通道单点开关」提升为**全局判定档位**，并明确 strict 仅作用于结构化槽位。

### 12.7 七组回归暴露的**三处过度脱敏**（已修复）

首轮七组回归（批次二落地后）暴露 4 处过度脱敏。逐条定位后**根因有三条**，
其中 G7 一处是**批次一遗留的结构性缺陷**（本批次因 D-8 提前处理「平安银行」而被暴露）。

#### 缺陷 A（G4）：槽位/角色条目以连词起首 → 伪姓名

- **现象**：`质量管理补充流程审核和发布` → `质量管理补充流程审核XXX`
- **根因**：「和」既是真实姓氏（He），又是极高频连词。D-5 槽位强判别与
  职务姓名通道（`_ROLE_NAME_RE`）仅凭「姓氏起点」放行，
  「审核」后的「和发布」被判为人名。
- **修复**：新增 `_SLOT_HEAD_VETO`（起首虚词/连词否决集），
  在 `_slot_item_name_span` 与 `_role_repl` 两处同时生效。
  取值刻意收窄为「几乎不作为姓氏」的虚词（和/与/及/或/但/则/若/因/所/被/把/将/且/而），
  **于/向/石/单/谷 等真实姓氏不在其中**，避免漏脱真实人名；
  D-5 兜底名单通道（`extra_name_list`，人工确认真名）不受此约束。
- **验证**：`审核：张三、李四`→`审核：XXX、XXX`、`负责人：刘兆缋`→`负责人：XXX`、
  `组长：王组长`→`组长：XXX` 均正常；4 条连词起首样本全部原样保留。

#### 缺陷 B（G5）：D-9 口令语义词跨单元格命中 + 复合业务编号被误脱

- **现象**：`（050103-往账处理）` → `（******-往账处理）`；
  `（051512-网银跨行转账异常处理）` → `（******-…）`
- **根因**：两条叠加——
  ① D-9 数字正则 `(?<![\w.])(\d{6,8})(?![\w.])` 只排除 `\w`，**`-` 不在其中**，
  故「数字-中文描述」形态的复合业务编号被当作独立数字；
  ② 口令语义词原按**整行**扫描，而 XML 感知路径下整份 sheet 被当作一条长行，
  A1 单元格的「账号」会让 B31 的业务编号一并脱敏。
- **修复**：
  ① 新增 `_is_compound_business_code`——数字后接「`-` + 中文」判为复合业务编号，保留；
  ② `_digit_segment_bounds` 的分隔符由「tab/`|`」扩展为「tab/`|`/`<`/`>`」
     （XML 标签边界天然对应单元格/文本节点边界）；
  ③ 语义词判定由「整行」收窄为「**同片段** 或 **邻近窗口**（前 60 字 / 后 40 字，
     且窗口内 XML 标签数 ≤ 2）」——既保住「相邻单元格（标签-密码 / 密码-值）」的召回，
     又阻断「整张 sheet 任意单元格命中」。
- **验证**：4 条复合业务编号样本原样保留；相邻单元格场景
  `<c r="A1"><v>登录密码</v></c><c r="B1"><v>888888</v></c>` 仍脱敏为 `******`；
  复现原缺陷的 XML（A1=账号管理说明 / B31=050103-往账处理）业务编号完整保留。

#### 缺陷 C（G7）：连词正则的**分组缺陷**（批次一遗留，本批次暴露）

- **现象**：`为保证监管单位及时掌握平安银行…` → `为保证监管单XXX及XXX掌握XX银行…`
- **根因（结构性）**：`_get_role_conjunction_re()` 中
  `surname_alt = "|".join(re.escape(c) for c in sp)` 拼接后**未加非捕获组**，
  正则被解析为 `(丁|万|…|刘[名用字]{1,3})`——`{name_class}{1,3}` 只挂在
  **最后一个姓氏分支**上，其余姓氏可「**零名用字**」单字命中。
  于是「位」（姓氏）+「及」（连词）+「时」（姓氏）即触发，
  整段被替换为 `XXX及XXX`。
  这是**批次一即存在的正则分组缺陷**，此前因上游通道先行处理而未暴露；
  本批次 D-8 提前处理「平安银行」，把它推到了台面上。
- **修复**：`surname_alt` 改为 `"(?:" + "|".join(...) + ")"`，
  语义回归设计意图「姓氏字 + 1~3 名用字」，两侧各一。分组数仍为 3（`test_name_false_positive`
  的 `pattern.groups == 3` 断言保持通过）。
- **验证**：`为保证监管单位及时掌握投产情况` 原样保留；
  `王力和张明` → `XXX和XXX`、`李四和王五` → `XXX和XXX` 仍正常脱敏。
