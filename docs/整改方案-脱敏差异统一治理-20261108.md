## 一、为什么需要合并整改

比对报告与 5 条 issue 描述的是**同一批缺陷的不同切片**。若按 issue 各自并行实施，会出现三处结构性冲突：

| 冲突点 | 涉及 issue | 冲突性质 |
|---|---|---|
| **同根因、两条通道** | #58（名单通道 `_apply_plain_list_pass`）、#59（锚点扩散通道 `_apply_anchor_expand_pass`） | 根因同为「缺人名证据判据」，若分别实现两套门控，将出现双重判定、行为不可预测 |
| **层与层重叠** | #57（规则C 长度量词）、#60（字池覆盖 + 频次闸门） | #57 修的是**匹配长度**，#60 修的是**字形覆盖**；#60 的验收明确依赖 #57 先落地（issue 原文已声明） |
| **组织名归属交叉** | #59（槽位内职务标签）、#61（机构名通名+后缀） | 「计财部」既可能被槽位通道处理、也可能被机构通道处理，缺少统一归属会重复脱敏或互相豁免 |

**结论**：改为「**一次证据层改造 + 三批场景接线**」，5 条 issue 降级为该方案下的 5 个子任务。

## 二、实测复核：issue 描述与实现的偏差

整改前对 5 条 issue 的每条根因做了代码级复核，**发现 3 处偏差**，直接影响方案设计：

### 偏差 1：#61 根因 2 不成立（保护表**已接线**，问题在语义参数）

issue #61 原文：

> 实测 `cr._is_protected_by_common_word_guard('科技部', 0, 4)` 返回 `True`，
> 但**组织名通道根本没有调用该守卫**——保护表只接入了姓名通道。

实测复核（`scripts/common_rules.py:2825`）：

```python
def _org_name_repl(m):
    if _is_protected_by_common_word_guard(m.string, m.start(), m.end(),
                                          strict_longer=True):   # ← 已调用
        return m.group(0)
    return rep.get("ORG", "XXXX")
```

**组织名通道确实调用了守卫**，但传的是 `strict_longer=True`。该参数的语义是「只有表内词**严格长于**命中片段才算豁免」——即「科技部」片段与表内词「科技部」**等长**，故不豁免。

| 调用形式 | `科技部` 结果 | 语义 |
|---|---|---|
| `_is_protected_by_common_word_guard('科技部',0,4)` | `True` | 等长即豁免（issue 打印的是这个） |
| `_is_protected_by_common_word_guard('科技部',0,4,strict_longer=True)` | `False` | 等长不豁免（**通道实际用的**） |

**真实根因**是「G4-S 前缀成词整体保留」策略与「通用词保护表」两条规则的**语义优先级未定义**，而非接线遗漏。修复点因此从「补接线」改为「定义优先级 + 拆表」（见 §4 批次二 D-2）。

> 连带说明：`strict_longer=True` 是 Issue #53 §3.2 的有意设计（否则「科技部」这类独立组织词永不被脱敏）。因此**不能简单改为 `False`**——那会使「信息科技部」这类前缀成词场景同时失去保护。正确做法是把「独立通用词」与「前缀成词」拆成两张表。

### 偏差 2：#57 方案 A 的回退逻辑不完整

issue #57 方案 A：「贪婪匹配 + 尾部职务字回退」，规则描述为「匹配片段末字若为职务后缀字，则回退 1 字」。

原型实测（`scripts/verify_remediation_design.py` 第 2 节）：

| 输入 | issue 方案 A 预期 | 实测（回退 1 字） | 正确结果 |
|---|---|---|---|
| `负责人：蔡昀煜` | `XXX` | `XXX` ✅ | `XXX` |
| `组长：樊霖副组长` | `XXX副组长` | `XXX副组` ❌ | `XXX副组长` |

**回退 1 字不足以剥离「副组长」这类双字职务词**。正确解法是「回退到**职务词起点**」——即贪婪匹配后识别尾部长度 ≥2 的职务词整体剥离。原型验证：

```
负责人：蔡昀煜      → 负责人：XXX
组长：阮秋鸣        → 组长：XXX
成员：吴文静        → 成员：XXX
组长：黄宽钊        → 组长：XXX
组长：樊霖副组长    → 组长：XXX副组长      ← 职务词整体保留
副组长：各条线副行长、总监 → 副组长：各条线副行长、总监   ← 整段不动
领导：总经理        → 领导：总经理
```

## 三、核心设计：证据分层模型

当前实现的判定逻辑是**枚举式豁免**——「形态像敏感实体 → 逐块找豁免理由 → 找不到就脱」。这是中文场景下的结构性缺陷：并列短语的组合无穷，穷举保护表必然漏（这正是 #58 观察到的现象）。

改为**证据分层**，按四层组织，每层的判据、优先级与失败兜底均显式定义：

| 层 | 名称 | 判据 | 缺省动作 |
|---|---|---|---|
| **L1** | 姓名证据层 | D16 全名 / 通用人名词典 / 姓氏+名用字(+字频闸门) / 上下文锚点 | 无证据 → **不脱** |
| **L2** | 职务标签层 | `prefix_forms + suffixes` 组合式声明（#59 方案） | 命中 → **整体保留** |
| **L3** | 机构实体层 | `org_stems + org_suffixes` 组合式 + 简称映射（#61 方案 A/C） | 命中 → **整段脱敏** |
| **L4** | 通用词护栏层 | 业务词表 / 保密标识短语 / 通用并列短语 / 边界对 | 命中 → **整体保留** |

### L1 的关键修正：证据判据必须叠加字频闸门

issue #58 的证据判据第 3 条为「该块首字 ∈ 实证姓氏集，且其余字 ∈ 名字用字池」。**实测该判据单独使用会引入误判**：

| 词 | 首字是姓？ | 余字在名用字池？ | 朴素判据 | 叠加字频闸门 |
|---|---|---|---|---|
| `方案设计` | ✅（方） | ✅ | **误判为姓名** | 正确排除 |
| `金融同业` | ✅（金） | ✅ | **误判为姓名** | 正确排除 |
| `日常运营` | ❌ | ✅ | 正确排除 | 正确排除 |
| `内部资料` | ❌ | 部分 | 正确排除 | 正确排除 |

原型实测（`scripts/verify_remediation_design.py` 第 1 节，40 个样本）：

```
正向样本（真名，应判 True）：16 例 → 命中 12 例
  未命中 4 例：李熔、王谧、成葭、刘兆缋  ← 均为字池缺字，属 #60 范畴
负向样本（职务标签/通用词，应判 False）：24 例 → 误判 0 例
```

**结论**：L1 判据必须写成「姓氏 ∈ surname_pool **且** 余字 ∈ name_pool **且** 尾字字频 ∈ hot∪warm **且** 非业务词/护栏词」，四者缺一不可。这与 #60 方案 1 的「GB2312 全量入池需与保护表双向互斥」是同一风险的两种解法——**叠加闸门的方案风险显著更低**，应作为首选。

### L1/L2/L3 的缺省方向不对称（设计取舍）

| 场景 | 判定方向 | 理由 |
|---|---|---|
| **结构化槽位**（角色锚点后、名单块内） | **默认保留，需正向证据才脱**（strict） | 一处漏脱 = 可追溯的单点事件，走人工复核；一处误伤 = 大面积不可预期的可用性事故（如 64 页 PPT 页脚全被抹）。两者不同量级，缺省应倒向可追溯一侧 |
| **非结构化正文** | **默认宽松，配合上下文锚点召回**（loose） | 正文叙述型人名（"XX行长指示…"）不在名单区、无槽位，严格模式会造成系统性漏脱 |

> #58 §六 已提出 `list_evidence_gate.mode: strict/loose` 的双档设计，方向正确。本方案将其从「名单通道单点开关」提升为**全局判定档位**，并明确 strict 仅作用于结构化槽位。

### 12.7 七组回归暴露的**三处过度脱敏**（已修复）

首轮七组回归（批次二落地后）暴露 4 处过度脱敏。逐条定位后**根因有三条**，
其中 G7 一处是**批次一遗留的结构性缺陷**（本批次因 D-8 提前处理「平安银行」而被暴露）。

#### 缺陷 A（G4）：槽位/角色条目以连词起首 → 伪姓名

- **现象**：`质量管理补充流程审核和发布` → `质量管理补充流程审核XXX`
- **根因**：「和」既是真实姓氏（He），又是极高频连词。D-5 槽位强判别与
  职务姓名通道（`_ROLE_NAME_RE`）仅凭「姓氏起点」放行，
  「审核」后的「和发布」被判为人名。
- **修复**：新增 `_SLOT_HEAD_VETO`（起首虚词/连词否决集），
  在 `_slot_item_name_span` 与 `_role_repl` 两处同时生效。
  取值刻意收窄为「几乎不作为姓氏」的虚词（和/与/及/或/但/则/若/因/所/被/把/将/且/而），
  **于/向/石/单/谷 等真实姓氏不在其中**，避免漏脱真实人名；
  D-5 兜底名单通道（`extra_name_list`，人工确认真名）不受此约束。
- **验证**：`审核：张三、李四`→`审核：XXX、XXX`、`负责人：刘兆缋`→`负责人：XXX`、
  `组长：王组长`→`组长：XXX` 均正常；4 条连词起首样本全部原样保留。

#### 缺陷 B（G5）：D-9 口令语义词跨单元格命中 + 复合业务编号被误脱

- **现象**：`（050103-往账处理）` → `（******-往账处理）`；
  `（051512-网银跨行转账异常处理）` → `（******-…）`
- **根因**：两条叠加——
  ① D-9 数字正则 `(?<![\w.])(\d{6,8})(?![\w.])` 只排除 `\w`，**`-` 不在其中**，
  故「数字-中文描述」形态的复合业务编号被当作独立数字；
  ② 口令语义词原按**整行**扫描，而 XML 感知路径下整份 sheet 被当作一条长行，
  A1 单元格的「账号」会让 B31 的业务编号一并脱敏。
- **修复**：
  ① 新增 `_is_compound_business_code`——数字后接「`-` + 中文」判为复合业务编号，保留；
  ② `_digit_segment_bounds` 的分隔符由「tab/`|`」扩展为「tab/`|`/`<`/`>`」
     （XML 标签边界天然对应单元格/文本节点边界）；
  ③ 语义词判定由「整行」收窄为「**同片段** 或 **邻近窗口**（前 60 字 / 后 40 字，
     且窗口内 XML 标签数 ≤ 2）」——既保住「相邻单元格（标签-密码 / 密码-值）」的召回，
     又阻断「整张 sheet 任意单元格命中」。
- **验证**：4 条复合业务编号样本原样保留；相邻单元格场景
  `<c r="A1"><v>登录密码</v></c><c r="B1"><v>888888</v></c>` 仍脱敏为 `******`；
  复现原缺陷的 XML（A1=账号管理说明 / B31=050103-往账处理）业务编号完整保留。

#### 缺陷 C（G7）：连词正则的**分组缺陷**（批次一遗留，本批次暴露）

- **现象**：`为保证监管单位及时掌握平安银行…` → `为保证监管单XXX及XXX掌握XX银行…`
- **根因（结构性）**：`_get_role_conjunction_re()` 中
  `surname_alt = "|".join(re.escape(c) for c in sp)` 拼接后**未加非捕获组**，
  正则被解析为 `(丁|万|…|刘[名用字]{1,3})`——`{name_class}{1,3}` 只挂在
  **最后一个姓氏分支**上，其余姓氏可「**零名用字**」单字命中。
  于是「位」（姓氏）+「及」（连词）+「时」（姓氏）即触发，
  整段被替换为 `XXX及XXX`。
  这是**批次一即存在的正则分组缺陷**，此前因上游通道先行处理而未暴露；
  本批次 D-8 提前处理「平安银行」，把它推到了台面上。
- **修复**：`surname_alt` 改为 `"(?:" + "|".join(...) + ")"`，
  语义回归设计意图「姓氏字 + 1~3 名用字」，两侧各一。分组数仍为 3（`test_name_false_positive`
  的 `pattern.groups == 3` 断言保持通过）。
- **验证**：`为保证监管单位及时掌握投产情况` 原样保留；
  `王力和张明` → `XXX和XXX`、`李四和王五` → `XXX和XXX` 仍正常脱敏。

### 14.2 D-9：判据由「语义词」收紧为「双证据」

原口径只要在片段或邻近窗口里看到 `密码/口令/pwd/...` 就脱敏，导致**清单型业务号被连坐**
（G3 实测「账号：123123、206900、456456」中的人工标准版只遮盖形态化的 `123123`/`456456`，
**保留非形态的 `206900`**；我方原口径把 `206900` 一并遮成 `******`，属过度脱敏）。

本批次把判据改为：

| 证据 | 含义 | 例 |
|---|---|---|
| 形态证据 | 全同（`888888`）/ 周期重复（`123123`、`456456`）；**连号不算** | `123123` ✅ |
| 标签-值形态 | **口令类**标签词紧邻数字之前（可隔 `：:＝=、,，/／ \t`） | 「初始密码：888888」✅ |
| 语义邻近 | 邻近窗口（前 60 / 后 40 字）提供上下文，**不单独构成脱敏依据** | — |

两个易错点已固化：

1. **`账号/帐号` 被排除在标签-值触发词外**——账号是业务标识（与付款协议号同类），
   不是口令；它只保留在「语义邻近」词表里。
2. **正则边界不能用 `\w`**——Python 3 的 `\w` 在 Unicode 模式下**匹配汉字**，
   于是「默认初始密码为888888」这类中文紧邻的独立口令完全匹配不上（实测 `findall` 为 `[]`）。
   改为 ASCII 边界：`(?<![0-9A-Za-z.])(\d{6,8})(?![0-9A-Za-z.])`。

### 15.4 D-11 补强 B：专名网点语境判别（三步判别）

新通道 `_apply_named_org_keep_pass`，在管线中位于 **D-8 机构实体通道之后、
pre_patterns / 地址通道 / 姓名通道之前**（三者都会切分机构名），以**哨兵占位**、
流水线末尾统一还原。

判别步骤（**仅对精确命中专名网点词的机构名生效**，避免未知专名默认保留造成漏脱）：

| 步骤 | 判据 | 结论 |
|---|---|---|
| ① 精确匹配 `place_rules.named_org_keep`（三山/台江/洪山/福新/科技/温泉/晋江/鼓楼） | 命中 | 进入保留候选 |
| ② 更长前缀含地名性词 `place_rules.geo_org_prefixes` ∪ `org_name_rules.admin_divisions` | 命中 | **仍遮蔽**（福州三山支行 → XX支行） |
| ③ 清单语境（三判据任一成立） | 成立 | **仍遮蔽** |
| ③ 清单语境 | 均不成立 | **保留原文**（哨兵保护） |

清单语境三判据：

- 顿号机构链成员 **≥ 4**（如「叫号机」行 5 个机构）；
- 顿号机构链中存在**非专名**成员（链中出现行政区/通用机构成员即说明这是机构清单，
  如「总行营业部」「福清分行营业部」）；
- 位于**清单标记域**（`org_list_markers`：参演机构 / 演练网点 / 参演网点 /
  参与机构 / 演练机构 / 网点清单 / 机构清单 / 演练机构安排）之前。

哨兵机制同时解决「洪山支行」被姓名通道误吞成「XXX支行」的问题——哨兵串不可被
任何正则命中，下游通道无法再切分该机构名。哨兵采用**私用区码位**
（`\ue000` + `\ue100+idx` + `\ue001`），不复用 D-8 的 `\x00WBORGENT` 形态：
后者含 ASCII 字母，会被英文通道吞掉（实测 `WBORGKE` → `P`）。

**设计取舍（显式披露）**：

- 判据①采用**白名单**而非「未命中地名词典即保留」：未知专名仍走既有遮蔽路径，
  避免因词典缺失造成漏脱；代价是新出现的专名需人工补词。
- 清单语境判据 ③-1 的阈值 **≥4** 为对本轮语料的**经验拟合**（标准版「叫号机」行
  5 个机构被遮蔽，而「指定福新支行、科技支行、温泉支行执行」3 个被保留）。
  该阈值是**保守方向**上的取值——提高会漏遮蔽机构清单，降低会误保留清单内专名。
- 标准版自身存在人工标注不一致：同一「鼓楼支行营业部」在「应急取款」两处
  一处遮蔽、一处保留。本轮按**清单语境**统一处理（两处均遮蔽），
  相对标准版残留 1 处差异，已计入 15.6 残余归属。

## 十六、批次五 · D-7 实施记录（L3 机构实体层，Issue #64）

### 16.1 问题与机制设计

机构名通道此前只有两层语义：

| 层 | 表 | 口径 |
|---|---|---|
| L1 | `generic_words`（独立通用词） | **保留**原文（`运营部` / `科技部` / `管理部` / `营运管理部` …） |
| L2 | `composite_words`（前缀成词） | **整段脱敏**（`信息科技部` / `金融科技部`） |

「通名 + 后缀」组合（如 `零售部` / `贸金部` / `营运管理部`）既不在两张表里，
只能落到通用机构名正则的兜底分支 `(?<![一-龥])[一-龥]{2}(?:部|科|中心|管委会|办公室)(?![一-龥])`，
于是两种错误同时存在：

1. **过度脱敏**：通用部门名被整段遮盖（`零售部` / `贸金部` / `特资部` / `金市部` / `公司部`
   在人工标准版中**一律保留**）→ 构成 G3 over 的机构类来源；
2. **口径不可切换**：真实机构实体只能按通用词保留，业务侧无法要求其整段脱敏
   （#64 §四 验收第 1 条长期无法满足的根因）。

**D-7 方案（Issue #64 §三 方案 A）**：引入 L3 机构实体层。

```
org_stems（通名）× org_suffixes（后缀）→ 组合式生成候选机构实体
  ├─ 组合命中 且 在 entity_whitelist（业务侧白名单）内 → 整段脱敏（杜绝「营运XXXX」混合态）
  └─ 组合命中 但不在白名单                            → 整段保留（回退批次一通用词口径）
```

`composite_words`（D-4 前缀成词层）同属「整段脱敏」口径，由本层一并接管，
保证 `信息科技部` 在两层之间**只有一种口径**。

**实现要点**（`scripts/common_rules.py`）：

| 组件 | 作用 |
|---|---|
| `_get_org_entity_layer_sets()` | 返回 (脱敏集合 = 白名单 ∪ composite_words, 保留集合 = 组合生成 − 脱敏集合) |
| `_get_org_layer_combo_re()` | 组合正则缓存，**与配置对象 id 绑定**（切配置即重建，纳入 `reset_patterns()`） |
| `_is_org_layer_combo_span()` | 通用机构名通道守卫：命中片段若与某组合式实体相交 → **保留** |
| `_apply_org_entity_mask_pass()` | 白名单实体整段脱敏，产出 `\ue004XXXX\ue005` 哨兵包裹 |
| `_restore_org_entity_layer()` | 流水线末尾还原哨兵 |
| `_get_org_generic_name_ctx()` | 追加 D-7「脱敏形态」lookbehind 锚点 |

**两处关键边界陷阱**（实施中实测发现并规避）：

1. **哨兵包裹原文不能用于「保留」场景**——通用机构名正则仍能在哨兵内部匹配到原词
   （`\ue002零售部\ue003` 仍会被遮成 `XXXX`）。
   故 D-7 的「保留」决策**不改写文本**，改由 `_org_name_repl` 中的

## 十七、批次六实施记录（2026-11-10）· D-6 / Issue #60

### 17.1 问题与机制设计

**问题**：#60 §三 方案 1 要求「GB2312 一级 + 二级汉字全量作为名用字候选池」，
用于兜底「尾字落在温字 / 冷字档」的生僻字人名在**裸上下文**（无角色槽位、
无职务后缀、无名单结构）下的整名漏脱。

D-5（方案 2，槽位强判别）只覆盖**角色槽位内**的场景，槽位外泛化召回一直是
#60 的未闭合缺口——这正是 issue §三「为什么两条必须并行」的核心论证。

**机制**（`scripts/common_rules.py` → `_apply_rare_name_pass`）：

| 设计点 | 口径 |
|---|---|
| 候选池 | GB2312 **二级汉字**（3008 字，56–87 区）。**一级字不入池**——一级字（支撑/占比/软件/覆盖/经验）正是 #49 复评实证的误伤区 |
| 放行档 | `二级字 − L4 护栏表用字 − hot 集`（**含 warm 档二级字**） |
| 「不放宽 hot 集」的准确含义 | hot 集**内容与判定阈值完全不变**（仍由 D16 全名库自举，freq ≥ 12）；D-6 是**并列**的放行通道，不修改 hot/warm 分类结果 |
| 匹配形态 | **最大匹配**：`姓 + 1~3 个名字位用字` + 尾部 `(?![名字位用字])` |
| 放行条件 | 命中片段中必须**至少含一个放行档字**，否则本层不重复放行 |
| 双向互斥 | 候选池 ∩ L4 护栏表（`common_word_guards` ∪ `biz_guard_words`）= 空 |

**为什么放行档含 warm 字**：warm 档（3 ≤ freq < 12）的二级字被既有「尾字门槛」
拦死，正是 D-6 要救的对象——`韩晗`/`曹晗`/`孟芸`/`陈曦`/`蔡菁`/`阮榕` 的尾字
全部落在这一档。若放行档排除 warm，这批目标名会整片漏脱（实测抽样召回仅
3/50、4/200）。**「不放宽 hot 集」约束的是 hot 集本身，不是禁止本层复用 warm 字**。

**候选池生成（纯标准库）**：逐字节解码 `bytes((hi, lo)).decode("gb2312")`，
16–55 区 → 一级 3755 字，56–87 区 → 二级 3008 字，全量 6763 字。
不依赖任何外部数据文件或第三方词库（内网离线环境的硬约束）。

**误伤闸门（五道）**：

1. **通用词否决表**（`config.json` → `name_rare_char_layer.veto_words`，125 条）：
   「姓 + 二级字」构成的通用词（时髦/房檐/江豚/白鹭/黄鳝/钟馗/石斛/白茯苓…）整词保留。
   判定采用**位置重叠**而非全等——枚举否决词在原文中的**全部出现位置**，
   只要与匹配片段 `[s, e)` 有字符交集即否决。覆盖三类错位形态：
   - 前缀型：正则只切出「白茯」，否决词是「白茯苓」；
   - 后缀型：正则匹配到「于付梓」，否决词是「付梓」；
   - 内嵌型：正则从否决词**内部**起匹配（「武侯祠」→「侯祠」）。
2. **机构 / 地名后缀守卫**：尾字为「祠」等机构后缀字时保留（仅对**三字及以上**
   片段生效，避免误伤「丁祠」类真实人名）。
3. **残尾守卫**：命中片段的下一字若与片段构成**已知全名**（D16 全名库 ∪ 通用
   人名词典），说明本片段只是全名前缀 → 放弃本次匹配（宁可不脱，也不制造
   「XXX + 残字」形态，#57 口径）。
4. **边界守卫**：左右不得紧邻 ASCII 字母 / 数字。
5. **放行档字条件**：片段中无放行档字则不重复放行，避免「王总」类职务/称谓误判。

## 十八、批次七实施记录（2026-11-10）· G7 修剪回退 / Issue #75

### 18.1 问题与根因

**问题**：#60（D-6）关闭后遗留的正交缺口——尾字落在 **hot 档**的人名
（`周竹婷` / `杜钰` / `胡璐`）在**无槽位上下文**下仍整段泄漏：

```
该文件由周竹婷签署   →  该文件由周竹婷签署      （泄漏）
该文件由杜钰签署     →  该文件由杜钰签署        （泄漏）
该文件由胡璐签署     →  该文件由胡璐签署        （泄漏）
```

**根因（两层叠加）**：

1. **贪婪吞字**：规则 D（`(?<=由)`）、规则 E（动词锚点）、S3' 角色锚点层的
   名字位是 `姓氏 + 名字汉字{1,3}` 的**贪婪**形态，在「由 X 签署」上下文里
   把 `周竹婷**签**` / `杜钰**签**` 整体吞成一个匹配；
2. **G7 整段回退**：跨词边界守卫识别出「签署」跨词（命中末字 `签` + 右邻字
   `署` ∈ 词表）→ **整段回退保留原文** → 人名整段泄漏。

**为什么 D-6 结构性不覆盖**：D-6 是「GB2312 二级字」冷档放行通道，
而这三例的尾字 `婷` / `钰` / `璐` 均落在 **hot 档**（freq ≥ 12），
D-6「不放宽 hot 集」故不覆盖——这正是 #75 另立的原因（口径正交）。

**归属差异**：`周竹婷` ∈ **D16 精确全名库**（7416 条）；
`杜钰` / `胡璐` ∉ D16，但 ∈ **#55 通用人名词典层**（117201 条）。
因此修复必须同时覆盖两个真名来源。

### 18.2 机制设计：G7「修剪回退」（trim-back）

**落点**：`scripts/common_rules.py` → `_name_guard_sub_counted`（姓名规则组
统一替换入口）的 G7 分支——原逻辑 `return m.group(0)`（整段回退）改为
**先尝试修剪回退**。

**新增函数**：

| 函数 | 职责 |
|---|---|
| `_get_trimback_names()` | 已知真名并集 = D16 全名库 ∪ #55 通用人名词典 ∪ D15 注入名（带缓存） |
| `_find_trimback_name_span()` | 在命中片段内判定「可单独脱敏的已知真名前缀」，返回 `(start, end)` 或 `None` |
| `_trimback_redact()` | 执行部分替换：只把真名前缀替换为占位符，被吞尾字原样保留 |

**三重必要条件（缺一不可）**：

| 条件 | 内容 | 反例自检 |
|---|---|---|
| ① **左邻不跨词** | 真名首字与其左邻字不成词 | `指向真实` 中的「向真」虽在 #55 词典内，但左邻 `指` + `向` = **指向** 成词 → 被拒 → 误伤不增 |
| ② **吞字证据** | 命中末字与其右邻字成词（与 G7 B 分支同源），且真名后**恰好只多 1 个尾字** | `石艳平汇` → 前缀「石艳」后多 2 字 → 被拒 → 不制造「XXX平」残尾 |
| ③ **真名可信** | 该串是已知真名（D16 ∪ #55 词典 ∪ D15）、首字为姓氏字，且不被常用词 / 整词保护 / 业务词 / 独立成词守卫豁免 | 「报表」「方法」等通用词不在已知真名集合内 |

**效果**：

```
该文件由周竹婷签署   →  该文件由XXX签署
该文件由杜钰签署     →  该文件由XXX签署
该文件由胡璐签署     →  该文件由XXX签署
该文件由杜钰汇报     →  该文件由XXX汇报     （附带修复）
最后由石艳平汇总全组  →  最后由石艳平汇总全组  （不变：条件②拒绝，避免残尾）
验证…是否指向真实      →  验证…是否指向真实    （不变：条件①拒绝）
```
