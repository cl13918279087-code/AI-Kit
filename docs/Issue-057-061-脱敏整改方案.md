## 〇、总体判断

### 0.1 与上一轮结论的修正

上一轮报告按「误伤 512 处 / 漏脱 75 处」的框架排序问题，**这个框架本身有缺陷**：
它把「误伤」与「漏脱」并列，把两者都当成"精度问题"。但从银行投产口径看，
二者的法律后果完全不同：

| 类别 | 后果 | 监管定性 |
|---|---|---|
| **残留泄露**（脱敏后仍留有身份信息） | 敏感信息流出 | **合规事故**，可被监管直接认定 |
| **漏脱**（一个名字整体没脱） | 敏感信息流出 | 合规事故 |
| **误伤**（把非敏感内容抹了） | 文档可用性下降 | 质量问题，不构成泄露 |

本轮实证发现，原报告归类为「漏脱」的 75 处里，**存在一个此前完全未被识别的
第四类缺陷——「部分脱敏 / 截断残留」**：

```
负责人：蔡昀煜   →   负责人：XXX煜
组长：阮秋鸣     →   组长：XXX鸣
```

尾部单字 `煜`/`鸣`/`钊`/`信`/`静`/`晨` **仍留在文档里**。这不是"漏脱了一个名字"，
而是"脱敏了名字的三分之二，留下了能与人名库反查的唯一标识"——
在外部交付件上等同于**未脱敏**，而在内部审计视角下它比"整体未脱"更危险：
因为审计台账会记录"姓名 ×1 已脱敏"，制造合规假象。

真实产出中的规模：g7 产出件存在 **406 处** `X{2,}[汉字]` 形态的截断残留，
g6 33 处，g1 18 处，g2 8 处。

**结论：整改优先级必须重排。** 原 P0-1（职务标签误伤）降为 P1，
新增 P0-1（截断残留）为第一优先级。

### 0.2 重排后的整改清单

| 新优先级 | 编号 | 问题 | 实测量级 | 后果 |
|---|---|---|---|---|
| **P0** | R-01 | 全角冒号后姓名匹配缺长度量词 → 三字姓名截断残留 | g7 406 处 / 全库 | **合规事故（隐蔽型）** |
| **P0** | R-02 | 顿号/逗号名单通道缺「人名证据」门控 → 页脚保密标识被抹 | g7 61 处 | 文档不可用 + 合规标识丢失 |
| **P0** | R-03 | 角色锚点扩散通道缺「槽位内容性质」判别 → 职务标签被当人名 | g1/g6/g7 366 处 | 文档不可用 |
| **P1** | R-04 | 名字位字池与频次闸门对低频生僻字系统性漏脱 | 15 例实名 | 合规事故（显性型） |
| **P1** | R-05 | 机构名通道「部分脱敏残留」与通用词误伤并存 | g3 102 处 | 口径不一致 + 不可用 |

> R-01 单独成条，因为它是**唯一带残留性质的**缺陷，验收标准完全不同。

## 一、R-01｜全角冒号后姓名匹配缺长度量词 → 三字姓名截断残留

### 1.1 现象

```
'负责人：蔡昀煜'  →  '负责人：XXX煜'     残留 1 字
'组长：阮秋鸣'    →  '组长：XXX鸣'       残留 1 字
'成员：吴文静'    →  '成员：XXX静'       残留 1 字
'由蔡昀煜负责'    →  '由XXX负责'          ← 规则D 有量词，正确
'负责人:蔡昀煜'    →  '负责人:XXX'         ← 半角规则C-1 有量词，正确
```

同一份文档中，仅因为冒号是全角还是半角，结果就不同 —— 这是规则设计缺陷的
典型特征（两条并列规则的口径未对齐）。

### 1.2 根因（精确到代码锚点）

`scripts/common_rules.py:3308-3318`　规则C：

```python
# 规则C：姓氏 + 1个名字汉字（左侧必须是全角冒号，解决"组长：樊霖"型漏检）
patterns.append((
    re.compile(
        rf'(?<=：)(?:{surname_alt}){name_char_class}'      # ← 缺 {1,3}
    ),
    rep.get("NAME", "XXX")
))
```

对比同文件内两条**并列**规则，口径明显不一致：

| 规则 | 位置 | 正则 | 长度量词 |
|---|---|---|---|
| 规则C-1（半角冒号） | `:3300` | `(?<=:)(?:姓){名}{1,3}` | ✅ 有 |
| **规则C（全角冒号）** | `:3316` | `(?<=：)(?:姓){名}` | ❌ **无** |
| 规则D（介词） | `:3328` | `(?<=由)(?:姓){名}{1,3}` | ✅ 有 |

规则C 的 `{1,3}` 量词是**在 Issue #49 P1 整改中被删掉的**——
当时的意图是「组长：樊霖副组长」这类「姓+1名字字+紧跟职务后缀」的场景
（若贪婪到 `{1,3}`，会把「樊霖副组」吞进姓名）。**这个意图是对的，
但实现方式错了**：正确解法是「贪婪匹配 + 尾部职务字回退」，
而不是「永久限制为 1 字」。

**代价**：所有「全角冒号 + 三字姓名」的场景，
无论是否在角色槽位内，都会被截断为 `XXX + 尾字`。

### 1.3 影响面量化

| 产出件 | `X{2,}[汉字]` 形态残留 | 说明 |
|---|---:|---|
| red_7 平安信用卡A+投产方案.pptx | **406** | 含 4 处 D15 表格姓名注入，注入量最大 |
| red_6 尖刀组UAT3测试规划.docx | **33** | 文档正文 + 表格 |
| red_1 启动会材料.pptx | **18** | |
| red_2 差异分析启动会.docx | **8** | |
| **合计** | **465 处** | |

其中已确认属**真实姓名尾字残留**（非对齐伪影）：

```
蔡昀煜 / 黄宽钊 / 阮秋鸣 / 段宇信 / 吴晋秋 / 易晓晨
董圣瑜 / 陈绍飞 / 费黎花 / 宗树峰 / 欧晓烨 / 李义申
吴文静 / 张锦宇 / 黄丽丹 / 廖腾华
```

对 `full_name_list` 随机抽样 400 条三字名复测：**0 条残留**
—— 说明 D16 精确层（整名匹配）不受影响，**受害的是全部 D16 库外人名**，
即真实生产环境中最需要被脱敏的那部分人。

### 1.4 建议方案

**方案 A（推荐，最小改动）**：规则C 恢复 `{1,3}`，同时在**回退**时排除职务尾字。

```python
# 名字位允许 1~3 字，但尾字不得为职务后缀字
_ROLE_TAIL = set("长员理监总组主任管经理行部长")
# 贪婪匹配后，若匹配片段的末字属于职务后缀，则回退 1 字
```

**已实测的行为对比**（在内存副本上验证，未改社区源码）：

| 输入 | 现状 | 方案A 贪婪 `{1,3}` | 方案B 贪婪 + 职务尾字排除 |
|---|---|---|---|
| `负责人：蔡昀煜` | `XXX煜` ❌ | `XXX` ✅ | `XXX` ✅ |
| `组长：樊霖副组长` | `樊` 被切 | `XXX副组长` ✅ | `XXX副组长` ✅ |
| `副组长：各条线副行长、总监` | 全抹 ❌ | **不变** ✅ | **不变** ✅ |
| `领导：总经理` | 不变 | **不变** ✅ | **不变** ✅ |

方案 A/B 均**不影响**职务标签场景（该场景由 R-03 单独处置），
也**不影响**「组长：樊霖副组长」的既有正确行为。

**方案 C（备选，需上游评审）**：不做长度恢复，改为在 `_apply_role_context_pass`
之后增加一道「尾部单字残留」扫描——若形如 `X{2,}[汉字]` 且该字为名用字，
则一并抹除。**不推荐**：属于事后补救，无法覆盖非角色槽位场景，
且会与真实的「XXX + 汉字」合法形态（如 `XXXX银` 地址前缀）混淆。

### 1.5 验收标准

1. `tests/test_issue57_colon_name_length.py`：
   - 上述 18 个实名在「全角冒号 + 角色槽位」「全角冒号 + 普通文本」
     「无冒号 + 介词」「半角冒号」四种上下文中**均不得出现残留尾字**；
   - `组长：樊霖副组长` 断言 `副组长` **完整保留**（防止修复引入新的职务误伤）；
   - `副组长：各条线副行长、总监` 断言**整段保留**（交由 R-03 验收）；
2. 全量 `full_name_list` 三字名回归：残留 **0 条**；
3. 通用语料误伤增量 **0**（相对基线）；
4. benchmark 门禁通过。

## 二、R-02｜顿号/逗号名单通道缺「人名证据」门控

### 2.1 现象

```
'内部资料，禁止外传'   →  'XXXX，XXXX'      ← 页脚保密标识被抹
'各方代表、专家骨干'   →  'XXXX、XXXX'      ← 业务表述被抹
```

g7（64 页 PPT）产出件中，页脚「内部资料，禁止外传」被整体抹除 **61 处**。

### 2.2 根因

`scripts/common_rules.py:4165`　`_LIST_NAME_RE`：

```python
_LIST_NAME_RE = re.compile(
    r"^[\u4e00-\u9fa5]{2,4}(?:[、，][\u4e00-\u9fa5]{2,4}){1,}$"
)
```

该正则**只描述形态，不含任何语义判据**：任意「2-4 字 CJK，用顿号/逗号连接」的
整行即命中。判定"这一块是不是人名"的责任被交给了下游三个守卫：

- `_RESIDUE_STOP`（残字虚词）；
- `_is_protected_by_biz_word`（业务词表，135 词）；
- `_is_protected_by_common_word_guard` / `_is_boundary_split_misfire`（Issue #51 保护表，330 词 + 2988 词边界对）。

**这三个守卫都是"逐块豁免"式**——没被表覆盖的块一律当作人名。
「内部资料」「禁止外传」「各方代表」「专家骨干」均不在表内，故被抹。

### 2.3 建议方案：正向证据门控（默认保留，反向证明才脱敏）

把判定方向从「形态像名单 → 逐块找豁免理由」反转为
「**先要求名单至少有一项具备人名证据，否则整行保留**」。

人名证据（满足其一即可，命中**任意一项**即认为该行是名单）：

1. 该块 ∈ `full_name_list`（D16 实证全名）；
2. 该块 ∈ `common_name_dict`（通用人名词典层，Issue #55）；
3. 该块首字 ∈ 实证姓氏集，且其余字 ∈ 名字用字池（`name_pool`）；
4. 该块在**角色锚点**（`组长：`/`负责人：`/`成员：`…）之后。

**已实测的门控行为**：

| 输入 | 块 | 证据 | 门控结果 |
|---|---|---|---|
| `内部资料，禁止外传` | 内部资料 / 禁止外传 | 无 / 无 | ✅ **保留** |
| `各方代表、专家骨干` | 各方代表 / 专家骨干 | 无 / 无 | ✅ **保留** |
| `报告生成、会议纪要` | 报告生成 / 会议纪要 | 无 / 无 | ✅ **保留** |
| `业务和技术骨干、外部专家骨干` | 业务和技术骨干 / 外部专家骨干 | 无 / 无 | ✅ **保留** |
| `窦磊、王富生、王根利` | 窦磊 / 王富生 / 王根利 | 有 / 有 / 有 | ✅ **脱敏** |

注意最后一行——真实名单**不会**因为加了门控而被漏掉，
因为 D16 精确层提供了正向证据。这正是 #49「名单块一致性」设计意图的延伸：
**名单的判定应该由"名单里的真名"来证明自己，而不是由"它长得像名单"来证明自己。**

### 2.4 附带收益

该门控同时解决原报告中的另一类误伤——
`组成` / `构成` / `协作` / `配置` / `风险` 等被切碎的业务动词短语，
它们多数出现在「A、B」并列结构中，同样会被名单通道吞掉。

### 2.5 验收标准

1. `tests/test_issue58_list_evidence_gate.py`：
   - 上述 5 条正反用例断言；
   - **回归保护**：真实名单（`窦磊、王富生、王根利`、`郑云、杨瑜`）
     仍**必须**被脱敏；
2. g7 产出件页脚「内部资料，禁止外传」**保留率 100%**（64/64 页）；
3. 真名金标召回**不低于**基线；
4. 通用语料误伤**下降**。

## 三、R-03｜角色锚点扩散通道缺「槽位内容性质」判别

### 3.1 现象

g1 原文段落：

```
组长：申学清常务副组长：孙海刚、毛月珍副组长：各条线副行长、总监成员：各业务部门总经理
```

程序输出：

```
组长：XXX清常务副组长：XXX、XXXXXX：XXXXXX、XXX：XXXXXX经理
```

- `孙海刚、毛月珍`（**人名**）→ 正确脱敏为 `XXX、XXXXXX`；
- `各条线副行长、总监`（**职务标签**）→ **被整段抹除** ← 误伤；
- `各业务部门总经理`（**职务标签**）→ 被抹为 `XXXXXX经理` ← 误伤 + 截断。

g6 原文：

```
副组长：朱丽琼、李杰     →  '副组长：XXX、XXX'        ✅ 正确
规划管理：李宁           →  '规划管理：XXX'           ✅ 正确
成员：业务和技术骨干、外部专家骨干  →  '成员：业务和技术骨干、XXXXXX'  ❌ 末块被抹
```

### 3.2 根因

`scripts/common_rules.py:4310`　`_apply_anchor_expand_pass`：

```python
for block_m in _NAME_BLOCK_RE.finditer(rest):     # ^[\u4e00-\u9fa5]{2,4}
    word = block_m.group(0)
    if word in _ANCHOR_EXCLUDED_NAMES: continue
    ...
    if _is_protected_by_common_word_guard(...): continue
    if _is_boundary_split_misfire(...): continue
    # → 全部通过则当作人名，直接替换
```

`_ANCHOR_EXCLUDED_NAMES` 只有 20 余个词的**枚举式排除表**
（"今日/一组/核心/开发/负责/参会…"），而槽位里的职务标签有数百种
（副行长、总监、总经理、常务副总、各条线副行长、外部专家骨干…）——
**枚举永远追不上组合爆炸**。

同时该通道**没有任何"这个槽位装的是人还是标签"的判据**：
槽位语义（角色锚点）是"这里可能有名字"，而不是"这里一定是名字"。

### 3.3 建议方案：槽位内容性质判别（两级）

**第一级：职务/角色标签词表显式声明**

在 `scripts/config.json` 新增 `role_label_patterns`，声明职务标签词：

```json
{
  "role_label_patterns": {
    "suffixes": ["行长","副行长","总行长","分行长","支行长","组长","副组长",
                 "经理","副经理","总经理","副总经理","总监","副总监","主任",
                 "副主任","科长","副科长","处长","副处长","主管","主管员",
                 "专员","顾问","助理","部长","副部长","处长","站长","队长"],
    "prefix_forms": ["各业务部门","各条线","外部专家","技术","业务","项目",
                     "专业","高级","初级","兼职","专职"],
    "composite_rule": "通名 + 职务后缀 → 整体视为职务标签"
  }
}
```

**第二级：槽位内容分型判定**

对角色锚点后的内容块，先分型再决定动作：

| 块类型 | 判据 | 动作 |
|---|---|---|
| **纯职务标签** | 命中 `role_label_patterns`（含通名+后缀组合） | **整体保留** |
| **纯人名** | 具备 D16 / 词典 / 姓氏+名用字证据 | 脱敏 |
| **混合**（"各条线副行长、总监"） | 逐块判定，职务块保留、人名块脱敏 | 分块处理 |
| **不可判定** | 无任何证据 | **保留**（宁可漏脱，不可误伤） |

**关键设计原则**：把「不可判定」的默认动作从"脱敏"翻转为"保留"。
在银行投产场景下，一处漏脱是**可追溯、可复核**的单点事件；
一处误伤是**大面积、不可预期**的可用性事故——
两者不同量级，默认值应当倒向可追溯的一侧。

> 但需注意：R-01 的截断残留恰恰是"漏脱"，与本原则冲突。
> 二者的解法不同——R-01 用**精确匹配**（贪婪 + 职务尾字回退），
> 本条用**保守判定**（无证据不脱）。二者不冲突：
> 前者解决"确定是名字却切错了"，后者解决"不确定是不是名字"。

### 3.4 验收标准

1. `tests/test_issue59_role_label_slot.py`：
   - g1/g6/g7 全部职务标签样例**逐字保留**；
   - 槽位内真实姓名**必须**仍被脱敏；
   - 混合槽位（"副组长：各条线副行长、总监" + "组长：孙海刚、毛月珍"）分型正确；
2. 职务标签误伤数 **366 → 0**；
3. 真名金标召回**不低于**基线。

## 四、R-04｜名字位字池与频次闸门对低频生僻字系统性漏脱

### 4.1 现象

15 个实名未被脱敏：`李熔`、`王谧`、`成葭`、`刘兆缋`、`欧晓烨`、`蔡昀煜`、
`俞曦`、`黄宽钊`、`阮秋鸣`、`段宇信`、`吴晋秋`、`易晓晨`、`廖腾华`、
`董圣瑜`、`陈绍飞`、`费黎花`、`宗树峰`、`吴文静`、`张锦宇`。

### 4.2 根因（两层，需分别处置）

**第一层：字池缺失**（4 例）

```
熔 / 谧 / 葭 / 缋   在 name_pool 中完全不存在（频次 0）
```

`name_pool` 当前 1283 字，是从项目语料自举的，**天然覆盖不到语料外的人名**。
这是**枚举式词表的结构性局限**，不是数据缺失。

**第二层：频次闸门误杀**（其余 11 例）

`common_rules.py:465` `_get_gated_name_chars()` + `:494` `_get_warm_name_chars()`：

| 名字 | 名字位字频 | hot(≥12) | warm(≥3) | 结果 |
|---|---:|:---:|:---:|---|
| 蔡昀煜 | 昀:4 煜:9 | ✗ ✗ | ✓ ✓ | 尾字非 hot → 整名不命中 |
| 黄宽钊 | 宽:5 钊:12 | ✗ ✓ | ✓ ✓ | 尾字 hot，但名字位为 2 字形态，`[温]{1}[热]` 未覆盖「宽+钊」？→ 实测截断 |
| 阮秋鸣 | 秋:23 鸣:17 | ✓ ✓ | ✓ ✓ | **字频充足仍被截断** ← 根因在 R-01 |
| 段宇信 | 宇:83 信:9 | ✓ ✗ | ✓ ✓ | 尾字信 freq=9 < 12 → 降为温字 |
| 吴晋秋 | 晋:5 秋:23 | ✗ ✓ | ✓ ✓ | 首字晋 freq=5 温 |
| 易晓晨 | 晓:158 晨:29 | ✓ ✓ | ✓ ✓ | **字频充足仍被截断** ← 根因在 R-01 |

**重要发现**：阮秋鸣、易晓晨的字频完全达标却仍被截断——
说明这部分漏脱的**真正根因是 R-01（长度量词）**，不是字频闸门。
把 R-01 修复后，此类漏脱**自动消失**。

这修正了原报告 P1-1 的归因（原报告把所有生僻字漏脱归为一类，
实际是两类问题叠加，优先级不同）。

**真正需要字池/闸门处置的只剩 5 例**：`李熔`、`王谧`、`成葭`、`刘兆缋`
（字池缺失）+ `段宇信`（尾字 freq=9 落入温档）。

### 4.3 建议方案

**方案 1（推荐）：GB2312 一级+二级汉字全量作为「名用字候选池」**

- 覆盖面：6763 字，覆盖中国内地全部人名用字（含生僻字）；
- **但不直接进 hot 集**——仍受频次闸门约束，只作为**兜底候选**；
- 与 `common_word_guards` / 保护表做**双向互斥**入库，
  避免"把常用字当名用字"造成误伤（这是 #49 的核心教训）。

**方案 2（推荐并行）：角色槽位内的姓名强判别**

在 R-03 的槽位分型中，若块为「2-4 字汉字串」且**位于角色锚点之后**，
即使字频不足也判为人名（槽位语义本身就是强证据）。
这一条能直接救回 `李熔`、`王谧`、`成葭`、`刘兆缋`，
且**不会**引入全局误伤（因为限定在角色槽位内）。

> 两条方案**互补不可互替**：方案 1 解决无槽位场景，
> 方案 2 解决有槽位场景；单用任一条都会残留漏脱。

### 4.4 验收标准

1. 上述 5 例在「角色槽位」与「无槽位」两种上下文中均被脱敏；
2. 通用语料误伤**不增加**（GB2312 全量入池的误伤风险必须被闸门挡死）；
3. 新增 `tests/test_issue60_name_char_coverage.py`：GB2312 生僻字抽样 ≥50 例召回率 100%。

## 五、R-05｜机构名通道：部分脱敏残留与通用词误伤并存

### 5.1 现象

```
'营运管理部'  →  '营运XXXX'      ← 部分脱敏：通名「营运」保留，机构名「管理部」被抹
'科技部'      →  'XXXX'          ← 通用词误伤（该词在 common_word_guards 中，但未生效）
'作战部'      →  'XXXX'          ← 通用词误伤
'运营中心'    →  'XXXX'          ← 通用词误伤
'信息科技部'  →  '信息科技部'      ← 漏脱（走银行名通道被整体豁免）
'自助渠道'    →  '自助渠道'        ← 保留（与标准版一致）
```

### 5.2 根因

**其一：通名+后缀是组合爆炸**。`org_suffixes` 只有 14 项
（部/中心/办公室/处/科/室/所/站/小组/科室/事业部/职能部门/分室/中心组），
而 `营运`/`零售`/`对公`/`计财`/`信息科技`/`运营` 等**通名**与 14 个后缀的
笛卡尔积就是数百种形态，逐一枚举不可行。

**其二：保护表与执行顺序脱节**。实测 `科技部` **已在** `common_word_guards` 中
（`_is_protected_by_common_word_guard('科技部', 0, 4)` 返回 `True`），
但组织名通道**根本没有调用该守卫**——保护表只接入了姓名通道。

**其三：部分脱敏残留**。`营运管理部` → `营运XXXX` 是"通名保留 + 机构名被抹"的
混合态，既不是完整脱敏也不是完整保留，属于**最坏的中间态**。

### 5.3 建议方案

**方案 A：机构名改为结构化模式（通名 + 后缀）**

```json
{
  "org_patterns": {
    "org_stems": ["营运","运营","零售","对公","计财","信息科技","风险","合规",
                  "授信","结算","资产负债","个人金融","公司","交易"],
    "org_suffixes": ["部","中心","室","处","科","组","团队","处室"],
    "composite": "org_stem + org_suffix → 整体脱敏（不留残尾）"
  }
}
```

同时新增**整段替换**语义：命中通名+后缀时，**整段一并替换**，
杜绝 `营运XXXX` 这类混合态。

**方案 B：组织名通道接入保护表守卫**

在 `_org_name_repl` 中前置调用 `_is_protected_by_common_word_guard`，
使已在保护表中的词（如「科技部」）不再被组织名通道吃掉。
这一条改动极小、收益直接。

**方案 C：机构简称派生**

`平安` → `平安银行`/`平安信用卡`；`计财` → `营运计财部`。
原报告列出的漏脱 `平安`(10 处)、`计财`(4 处)、`分行`(2 处) 属此类。
建议建立**品牌简称 → 全称**的映射表，命中简称即按全称口径脱敏。

### 5.4 验收标准

1. `tests/test_issue61_org_pattern.py`：
   - `营运管理部` → 整段脱敏，**无残尾**；
   - `科技部` / `作战部` / `运营中心` → 保留；
   - `平安` / `计财` → 按全称口径脱敏；
2. 「部分脱敏残留」形态（`XX + XXXX` 混合）出现 **0 次**；
3. g3 超标准覆盖 102 处下降 ≥70%。

## 七、落地建议（架构师意见）

### 7.1 批次划分

| 批次 | 内容 | 理由 |
|---|---|---|
| **第一批** | R-01（截断残留） | 唯一带合规后果的缺陷，且改动最小、收益最大 |
| **第二批** | R-02 + R-03（误伤） | 同源语义判据，一起设计避免两次返工 |
| **第三批** | R-04 + R-05（召回与口径） | 需要词表/映射表输入，社区评审周期长 |

### 7.2 验收纪律（强烈建议写进上游贡献规则）

1. **残留零容忍**：任何整改后的产出件中，`X{2,}[汉字]` 形态残留必须为 **0**。
   这是可自动化的验收项，应加入 `tests/` 作为永久回归。
2. **误伤与漏脱分别设门禁**：误伤门禁（通用语料 FPR）与漏脱门禁
   （真名金标召回）必须**同时**通过，不得相互补偿。
3. **整改不得以牺牲另一侧为代价**：任何修复若导致另一侧指标下降超过 1pt，
   视为未完成——需重新设计而非调参。

### 7.3 对已交付件的影响提示

本轮发现的两类缺陷（R-01 截断残留、R-02 页脚误伤）**存在于已交付的历史产出件中**。
建议对已对外交付的脱敏件做一次**残留复扫**（正则 `X{2,}[汉字]`），
确认是否存在需要追回或补发的场景。这属于投产前的例行动作，
但必须显式执行，不能默认"应该没有"。
