## 一、P0 关键问题（必须修复）

### 1.1 API Key 未真实注入 — LLM 调用完全不生效

**位置**：`config.json`

```json
"api_key": "***"
```

`llm_client.py` 的 mock 模式判断逻辑：
```python
self.mock_mode = not bool(self.api_key)  # "***" → False → 走真实请求...❌
```

`"***"` 是非空字符串，`not bool("***") = False`，所以**走了真实请求路径**，但 key 是 `"***"` 本身。MiniMax API 收到 `Bearer ***` → **全部失败**，静默退回空结果或报错，但 `DEMO_MOCK_MODE` 日志一条都没有打印。

**实际表现**：工具声称在用 LLM 智能识别，实际上完全没有调用成功，只是 regex 层在跑。

**修复方案**：
```python
# llm_client.py __init__ 中加判断
if not self.api_key or self.api_key.strip() in ("", "***", "your-key-here"):
    self.mock_mode = True
```

### 1.2 editor_sdk 返回 file_id 被误用

**位置**：`editor_executor.py` 第 99 行

```python
def open_file(self, file_path: str) -> str:
    result = self._run("open_file", file_path=file_path)
    # ...
    return file_path  # ❌ 返回的是输入的路径，而非真实的 file_id
```

`pipeline.py` 后面的所有阶段都用这个返回值做 `file_id`，但 `editor_sdk` 真正的 file_id 是 JSON 响应里的字段（通常不是路径字符串）。后续所有 `get_document_content`、`execute_manifest` 传入的 `file_id` 都是错的。

**影响**：大文档场景下 editor_sdk 如果已修复合并问题，这里会导致整个 pipeline 失败。

---

### 1.3 subprocess shell=True 命令注入风险

**位置**：`editor_executor.py` 第 72 行

```python
cmd = f"{self.sdk_cmd} call {subcmd}"
proc = subprocess.Popen(cmd, shell=True, ...)
```

如果 `sdk_path` 或 `file_path` 包含恶意字符，会造成命令注入。

**修复**：用 `shlex.split` + `subprocess.run(shell=False)`。

### 1.4 图片马赛克使用已废弃的 LANCZOS

**位置**：`editor_executor.py` 第 179 行

```python
Image.Resampling.LANCZOS  # PIL 10+ 已废弃
```

应改为 `Image.Resampling.BICUBIC` 或 `Image.LANCZOS`（别名）。

## 二、P1 问题（严重影响金融合规性）

### 2.1 缺少监管合规性留痕机制

**问题**：银行监管要求脱敏操作必须**可追溯、可审计**。当前实现：

- `manifest.json` 保存了替换清单，但**无操作者身份**
- **无操作时间戳精确记录**（只有 manifest.generated_at，是生成时间而非操作时间）
- **无版本对照**（原文档 vs 脱敏后文档的完整 diff）
- **无法证明"哪个自然人在哪个时间点确认了哪项替换"**

**金融监管背景**：
- 银保监会《商业银行信息科技风险管理指引》要求重要操作留痕
- 银行间业务文档涉及行际竞争，泄露后责任认定困难

**建议**：
```python
@dataclass
class RedactionAuditRecord:
    operator_id: str          # 工号
    operator_name: str        # 姓名
    operation_time: str       # ISO 8601，含时区
    document_hash_original: str  # 原文档 SHA-256
    document_hash_redacted: str # 脱敏后 SHA-256
    approved_entities: list   # 人工确认的实体列表
    rejected_entities: list   # 人工拒绝的实体列表
    total_replacements: int
    machine_signature: str     # 脱敏工具版本签名
```

### 2.2 账号识别正则严重过度匹配

**位置**：`entity_detector.py` 第 47 行

```python
ACCOUNT_PATTERN = re.compile(r'\b(\d{10,20})\b')
```

**问题**：匹配**任意 10-20 位数字**，会误伤流水号、业务编号、页码、产品代码。

**金融场景**：银行内部系统有大量 10 位以上纯数字编码，错误替换后**文档完全无法阅读**。

**修复**：账号必须有明确的上下文标识（前后是"账号："、"账户："等），或结合标准银行账号格式（行号 + 币种 + 账号类型 + 序号）分段验证。

---

### 2.3 日期替换会破坏文档语义关联

**问题示例**：
```
原文：2022年4月8日至2022年4月10日
替换后：YYYY年MM月DD日至YYYY年MM月DD日
```

→ 原文告诉你"3 天的演练周期"，替换后完全丢失。

**修复**：增加语义感知模式，区分：
- 时间点（单独日期）→ 可替换
- 时间段/周期（日期范围）→ 替换后需保留相对关系
- 时间序列（第 N 轮/第几次）→ 保留顺序词，只替换具体日期

---

### 2.4 EXCLUDED_COMMON_WORDS 中"海峡"误排除

**位置**：`entity_detector.py` 第 73 行

```python
"海峡", "台湾海峡", "海峡两岸",
```

**问题**：排除列表是全局的，如果文档中同时出现"台湾海峡"和"海峡银行"，两者都会被排除：

- "台湾海峡" → 正确排除 ✅
- "海峡银行" → 被错误排除 ❌（会漏脱敏）

---

### 2.5 页眉页脚直接 mosaic 逻辑过于粗暴

**位置**：`pipeline.py` 第 160-167 行

```python
if img_type == "header_footer":
    # 页眉/页脚图片 → 直接 mosaic（无需 OCR）
    results.append({"action": "mosaic", ...})
```

**问题**：
1. 银行页眉通常只有 logo（无文字），mosaic 后丑化文档
2. 如果页眉恰好没有敏感信息，白白破坏文档外观
3. 应该先 OCR 判断，再决定是否 mosaic

### 2.6 Word 自定义属性（Core Properties）未处理

**问题**：Word 文档的以下位置可能含敏感信息，当前**完全未扫描**：

## 三、P2 问题（功能性缺陷）

### 3.1 `run_interactive_review` 中断 pipeline

**位置**：`pipeline.py` 第 248 行

```python
choice = input("...").strip().lower()  # ❌ 在 Web/服务模式下会崩溃
```

此方法设计为交互式 CLI，但在 `app.py` 的 Web 流程中从未被调用，且没有 fallback。一旦误触发，进程挂起。

---

### 3.2 `main()` 中 `manifest` 变量引用错误

**位置**：`pipeline.py` 第 292 行

```python
print("\n" + manifest.summary() if "manifest" in dir() else "")
```

`manifest` 是局部变量，从未在 `main()` 函数作用域内定义，永远走 else 分支。

---

### 3.3 Phase 5 验证逻辑矛盾

**位置**：`pipeline.py` 第 199-205 行

**问题**：
1. `dry_run=True` 时跳过验证 → 什么也没验证
2. `dry_run=False` 时，如果 editor_sdk 替换未落盘（已知 P0 问题），验证拿到的是未替换的原文本，验证通过是**假阳性**

---

### 3.4 `app.py` 会话管理在内存中，重启丢全部状态

**位置**：`app.py` 第 75-90 行

生产环境中 uvicorn 进程重启，所有上传文件路径、manifest、file_id 全部丢失。

**金融场景**：银行通常要求操作中途断可续办。

---

### 3.5 `_split_for_llm` 跨块重叠导致实体被切断

**位置**：`entity_detector.py` 第 258-269 行

```python
# 保留最后一个作为上下文重叠
current = [current[-1]] if len(current) > 1 else []
```

只重叠了最后一行，如果一个人名跨越了两个 chunk 的边界，会被切成两段 → LLM 无法识别。

**修复**：每个 chunk 前后各重叠 200-500 字符，或按段落（`\n\n`）切分而非逐行累积。

---

### 3.6 多语言扩展未集成

**位置**：`extensions/multi_lang.py`

`entity_detector.py` 的 `detect_from_text` **从未调用** 多语言检测。如果银行文档含英文联系人姓名或英文银行名，完全不会处理。

---

### 3.7 `templates.py` 行业模板未集成

**位置**：`extensions/templates.py`

`TemplateManager.build_industry_prompt()` 生成了行业专用 Prompt，但 `prompts.py` 的 `ENTITY_EXTRACTION_SYSTEM_PROMPT` 是**硬编码**的通用版，未通过 `TemplateManager` 动态注入。

## 四、P3 问题（改进建议）

### 4.1 缺少单元测试

整个包**零测试**。生产级金融工具必须有：
- 正则规则测试（用已知样本验证各日期格式匹配/不匹配）
- Manifest 去重测试
- Pipeline 各 phase 的 mock 测试
- 误脱率测试

### 4.2 Tesseract 路径硬编码

**位置**：`ocr_processor.py` 第 36 行

```python
self.tesseract_cmd = self.ocr_cfg.get("tesseract_cmd",
    "/opt/homebrew/bin/tesseract")
```

仅 macOS Homebrew 路径，Linux、Windows 环境均不适用。

### 4.3 OCR 无批处理能力

**位置**：`ocr_processor.py` `batch_analyze` 方法

图片 OCR 是独立任务，应并行执行，可用 `concurrent.futures.ThreadPoolExecutor`。

### 4.4 WPS 格式支持是空白

`app.py` 表单接受 `.wps`，但 pipeline 中无任何 WPS 解析逻辑。

### 4.5 缺少 PDF 支持

银行对外报送文档大量使用 PDF，当前包完全不支持。

## 六、合规性总评

| 维度 | 当前状态 | 银行合规要求 | 差距 |
|------|---------|-----------|------|
| **可追溯性** | ❌ 无操作日志 | 操作留痕（人+时间+操作内容） | 重大 |
| **准确性** | ⚠️ 部分保障 | 误脱率<0.1%，漏脱率=0 | 中等 |
| **完整性** | ⚠️ 表格/姓名/日期已修，图片/元数据未处理 | 全内容覆盖 | 中等 |
| **一致性** | ⚠️ demo key 导致全 mock | 所有文档同等质量 | 严重 |
| **版本控制** | ❌ 无 | 原文档与脱敏版本一一对应 | 重大 |
| **自动化测试** | ❌ 零测试 | 回归测试套件 | 重大 |

## 八、总结

这套工具在**单一银行、单一文档格式、中等复杂度**场景下已经跑通了核心链路（Phase 1-6 全通），尤其是表格 block 结构问题、日期正则问题、角色词姓名推断的解决思路是正确的，具备金融文档脱敏的基础能力。

但距离**金融行业生产级合规工具**还有三道槛：

1. **真实 LLM 调用**——当前 api_key 注入机制完全失效，实际上只在跑正则
2. **监管留痕**——无审计记录是无法通过任何银行合规审查的
3. **账号/日期误脱**——这两类误脱一旦进入生产文档，轻则返工，重则引发合规事故

建议以 **P0 + P1** 作为下一版本（v1.0）的发布门槛。
